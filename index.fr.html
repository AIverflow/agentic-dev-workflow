Avant de commencer

Les bases

🤖

Qu'est-ce qu'un agent de code ?

Un assistant IA qui travaille dans le dossier de votre projet. Il lit vos fichiers, écrit du code et lance des commandes, comme un collègue assis à votre ordinateur. Exemples : Claude Code, Codex, Cursor.

🧩

Qu'est-ce qu'un skill ?

Une fiche recette que l'agent suit pour une tâche précise. On lance un skill en tapant une barre oblique suivie de son nom, par exemple /grill-with-docs.

⚙️ Installation : une fois par projet, environ 5 minutes

Ça transforme un projet normal en un projet où votre agent travaille bien. Marche sur un projet neuf ou existant.

1

Installer les skills (une fois par ordinateur)

Demandez simplement à votre agent :

Installe les skills de Matt Pocock (mattpocock-skills, depuis le marketplace officiel de plugins Claude).

Marche avec la plupart des agents de code. Source : github.com/mattpocock/skills

2

Donner un guide du projet à l'agent : /init

La plupart des agents ont une commande init. L'agent parcourt votre projet et écrit un fichier guide (CLAUDE.md ou AGENTS.md, selon l'agent) : comment lancer, tester et construire le projet, et où se trouvent les choses. L'agent le lit au début de chaque session.

3

Brancher les skills : /setup-matt-pocock-skills

Pose 2–3 questions, puis ajoute une section « Agent skills » à votre guide et écrit quelques petits fichiers de config dans docs/agents/.

Quand il demande où ranger les tickets, choisissez fichiers locaux. Pas besoin de compte GitHub.

✅ C'est prêt. Votre projet est paré pour les 6 étapes ci-dessous.

💡 Pourquoi suivre un workflow ?

La raison n°1 pour laquelle le code avec l'IA tourne mal : l'agent construit quelque chose, mais pas ce que vous vouliez. La solution : ralentir au début. On se met d'accord sur l'idée, on l'écrit, on la découpe en petits morceaux, et seulement ensuite on code.

Pensez à la construction d'une maison : 🗣️ discussion avec l'architecte → 📐 plan → 📋 bons de travaux → 🧱 construction, avec des contrôles en cours de route → 🔍 inspection finale → 🪞 débrief d'équipe.

🔥 Grill with docs→ 📄 Spec→ 🎟️ Tickets→ 🛠️ Code + TDD→ 🔍 Revue→ 🪞 Rétro

📌 Notre exemple du début à la fin : ajouter un mode sombre à une petite app de liste de tâches.

🔥
Étape 1

Grill me (with docs)

/grill-with-docs

L'agent vous interroge avec plein de questions jusqu'à ce que vous soyez d'accord sur ce qu'il faut construire, et note au fur et à mesure le vocabulaire du projet et les grandes décisions.

🏠 Comme un bon architecte qui demande « Combien de chambres ? Grande cuisine ou petite ? » avant de dessiner quoi que ce soit.

Vous
  • Décrivez votre idée en une phrase
  • Répondez à chaque question (des réponses courtes suffisent)
  • Dites « je ne sais pas » quand c'est le cas. L'agent propose une réponse.
Agent
  • Pose les questions par petites séries
  • Propose une réponse recommandée pour chacune
  • Continue jusqu'à ce que plus rien ne soit flou
  • Met à jour le glossaire (GLOSSARY.md) et les notes de décision (docs/adr/)
Exemple
Agent de code : todo-app
Vous
/grill-with-docs Je veux ajouter un mode sombre à mon app de tâches
Agent

Q1 : Doit-il suivre le réglage clair/sombre de l'ordinateur, ou passer par un bouton ? → Je recommande les deux : suivre l'ordinateur par défaut, avec un bouton pour changer.

Q2 : L'app doit-elle se souvenir de votre choix après un rechargement ? → Oui.

Vous
Les deux, oui. Et oui, garde le choix en mémoire.
Agent

Série suivante. Q3 : Où placer le bouton ?…

Ce qu'il écrit en chemin
GLOSSARY.mdThème : le jeu de couleurs utilisé par l'app, « clair » ou « sombre ». Thème système : le réglage clair/sombre de l'ordinateur de l'utilisateur.

Pourquoi c'est utile : la prochaine fois, vous et l'agent utilisez les mêmes mots pour les mêmes choses. Moins de malentendus, des réponses plus courtes. (/grill-me tout court fait l'interview sans les docs. Pratique pour les sujets hors code.)

💡

Astuce : c'est l'étape que tout le monde saute, et c'est la plus importante. Dix minutes de questions évitent des heures à corriger la mauvaise chose. Utilisez-la à chaque fois.

📄
Étape 2

Écrire la spec

/to-spec

L'agent transforme votre conversation en plan écrit (une « spec »). Pas de nouvelles questions, il écrit juste ce que vous avez décidé.

🏠 Le plan de la maison. Tout le monde peut le relire plus tard et vérifier « c'est bien ce qu'on avait dit ? »

Vous
  • Lancez-le juste après l'interview, dans la même conversation
  • Validez comment l'agent compte tester la fonctionnalité
  • Lisez la spec. Corrigez ce qui ne va pas.
Agent
  • Parcourt votre code
  • Écrit la spec dans un fichier
  • Liste aussi ce qui est hors périmètre
Exemple : ce que l'agent écrit
.scratch/dark-mode/spec.md## Problème L'app est trop lumineuse le soir. ## Solution Un thème sombre qui suit le réglage de l'ordinateur, avec un bouton pour basculer. ## User stories 1. En tant qu'utilisateur, je veux l'app en sombre quand mon ordinateur est en mode sombre… 2. En tant qu'utilisateur, je veux un bouton pour changer de thème… 3. En tant qu'utilisateur, je veux que mon choix soit gardé après rechargement… ## Hors périmètre Couleurs personnalisées, mode sombre automatique au coucher du soleil.
💡

Astuce : la spec, c'est votre document. Si quelque chose cloche, dites-le maintenant. Corriger une phrase coûte bien moins cher que corriger du code.

🎟️
Étape 3

Découper en tickets

/to-tickets

L'agent découpe la spec en petits tickets. Chacun est un petit morceau qui fonctionne tout seul.

🏠 Les bons de travaux : « plomberie de la cuisine », « électricité de la chambre ». Une équipe, une tâche, une journée.

✅ Bien : des parts

01
02
03

Chaque ticket traverse toutes les couches (écran, logique, sauvegarde) pour une petite fonctionnalité. On peut l'essayer dès qu'il est fini.

❌ Mal : des étages

tous les écrans
toute la logique
toute la sauvegarde

« D'abord tous les écrans, puis toute la logique… » Rien ne marche avant la toute fin.

Vous
  • Vérifiez la liste proposée
  • Trop gros ? Trop petit ? Demandez de découper ou de fusionner.
  • Validez
Agent
  • Propose les tickets, dans l'ordre
  • Indique quel ticket doit attendre lequel
  • Enregistre un fichier par ticket
Exemple : les tickets du mode sombre
01
Un bouton change le thème
Attend : rien, on peut commencer
02
Garder le choix après rechargement
Attend : 01
03
Suivre le réglage de l'ordinateur par défaut
Attend : 01

Enregistrés sous .scratch/dark-mode/issues/01-toggle-button.md, 02-…, 03-…

💡

Astuce : chaque ticket est taillé pour tenir dans une session neuve de l'agent. Des petits tickets, c'est un agent concentré qui fait moins d'erreurs.

🛠️
Étape 4

Coder, en testant d'abord (TDD)

/implement

L'agent réalise un ticket en écrivant d'abord le test, puis le code qui le fait passer.

🏠 Avant de monter un mur, on écrit le contrôle : « le mur doit être droit ». On construit. On contrôle. Mur suivant.

La boucle TDD (développement piloté par les tests)

🔴 RougeÉcrire un test pour un petit comportement.
Il échoue, car le code n'existe pas encore.
→
🟢 VertÉcrire juste assez de code
pour que le test passe.
↻
RecommencerComportement suivant,
jusqu'à la fin du ticket.

Pourquoi ? Les tests donnent à l'agent une preuve que son code marche, au lieu de simplement y croire. Sans tests, il avance à l'aveugle.

Vous
  • Ouvrez une session neuve (/clear ou nouvelle conversation)
  • Indiquez un ticket à l'agent
  • Validez ce qui sera testé
  • Observez, et intervenez s'il part dans la mauvaise direction
Agent
  • Enchaîne la boucle rouge → vert
  • Lance tous les tests à la fin
  • Lance la revue (étape 5) tout seul
  • Enregistre le travail (commit git)
Exemple
Agent de code : todo-app (session neuve)
Vous
/clear
/implement .scratch/dark-mode/issues/01-toggle-button.md
Agent

🔴 Test : « cliquer sur le bouton de thème rend la page sombre ». Échoue, comme prévu.

🟢 Ajouté le bouton et les couleurs sombres. Le test passe.

🔴 Test : « cliquer deux fois revient au clair »… 🟢 passe.

✅ Tous les tests passent. Commit fait. Je lance la revue…

⚡ Option rapide : tous les tickets d'un coup avec /implement-spec

Au lieu d'un ticket par session, l'agent lance plusieurs agents assistants en parallèle. Chacun travaille dans sa propre copie du projet, un ticket chacun, en testant d'abord. Quand un ticket est fini, son travail est fusionné dans une branche commune. Les tickets en attente démarrent dès que ceux qui les bloquaient sont finis. À la fin, une seule revue de l'ensemble.

Idéal quand il y a beaucoup de tickets. Commencez par /implement, un ticket à la fois, jusqu'à ce que le workflow vous soit familier. C'est plus facile à suivre et à piloter.

💡

Astuce : envie de tester d'abord pour une petite correction hors de ce workflow ? Tapez juste /tdd. C'est la même boucle.

🔍
Étape 5

Revue de code

/code-review

Deux relecteurs séparés vérifient le travail. Le code est-il propre ? Et fait-il ce que le ticket demandait ?

🏠 L'inspection finale. Un inspecteur vérifie les normes de construction, un autre vérifie que tout correspond au plan.

📏 Standards

Le code suit-il les règles du projet ? Des noms clairs ? Pas de copier-coller ? Rien de trop compliqué ?

🎯 Spec

Fait-il tout ce que le ticket demandait, et rien de plus ? Quelque chose qui manque, qui est faux ou en trop ?

Vous
  • Lisez les deux rapports
  • Décidez quoi corriger : « corrige 1 et 3, ignore 2 »
Agent
  • Lance les deux relecteurs côte à côte
  • Signale les problèmes, sans rien corriger de lui-même
  • Corrige ce que vous choisissez
Exemple : rapport de revue
## Standards (1 point) - Nom peut-être peu clair : la variable `t` devrait s'appeler `theme`. ## Spec (1 point) - En trop : ajout d'un thème « sépia », que le ticket ne demandait pas.
💡

Astuce : /implement lance la revue pour vous à la fin. Pour la lancer vous-même, donnez un point de départ, par exemple /code-review main (tout ce qui a changé depuis la branche main).

🔁

Ticket suivant ? Retour à l'étape 4.

Session neuve → /implement ticket 02 → revue → ticket 03… jusqu'à ce que tous les tickets soient faits. Puis l'étape 6. 🎉

⚡ Beaucoup de tickets ? /implement-spec fait toute cette boucle d'un coup, en parallèle, avec une revue à la fin (voir l'étape 4).

🪞
Étape 6

Rétro : tirer les leçons de la session

/retro

L'agent revient sur le déroulé du travail et propose des façons d'améliorer sa propre configuration, pour que la prochaine fonctionnalité se passe mieux. Il change la configuration, pas le code.

🏠 Le débrief d'équipe une fois la maison finie : « Qu'est-ce qui nous a ralentis ? Qu'est-ce qu'on devrait vérifier automatiquement la prochaine fois ? »

Vous
  • Lancez-la quand tous les tickets sont faits, ou après une session difficile
  • Choisissez les suggestions à appliquer
Agent
  • Relit la session
  • Repère ce qui a été lent ou raté
  • Propose des corrections, les plus importantes d'abord

Ce qu'il cherche

🧭

Trouver les choses

L'agent a perdu du temps à chercher des fichiers ? Ajouter un repère dans le guide du projet.

🚦

Contrôles automatiques

Un linter, un test ou un contrôle avant commit aurait-il attrapé une erreur ? L'ajouter.

📏

Règles

La revue a raté quelque chose ? Ajouter une règle aux standards de code, ou en retirer une inutile.

Exemple
Agent de code : todo-app
Vous
/retro
Agent

1. Contrôles automatiques : j'ai fait un commit avec un test en échec. Ajouter un contrôle avant commit qui lance les tests.

2. Trouver les choses : j'ai fouillé 6 fichiers pour trouver les couleurs. Ajouter une ligne dans AGENTS.md : « Les couleurs du thème sont dans styles/theme.css ».

Vous
Fais les deux.
💡

Astuce : chaque rétro rend l'agent un peu meilleur sur votre projet. Les petites améliorations s'additionnent vite.
