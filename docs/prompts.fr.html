Prompts prêts à l'emploi

Copiez un prompt, remplissez les trous, puis collez-le dans une nouvelle session d'agent.

🧒 Expliquer simplement (ELI5)

À utiliser quand un sujet semble difficile. L'agent l'explique avec des mots simples, puis vérifie que vous avez compris.

À remplir : [SUJET] [CE QUE JE SAIS]

Expliquez [SUJET] à un débutant complet, comme si j'avais 5 ans.
Ce que je sais déjà : [CE QUE JE SAIS, ex. « j'utilise git mais je n'ai jamais entendu parler de rebase »].
- 150 mots maximum (sans compter les questions). Phrases courtes. Pas de jargon ; si un terme est inévitable, définissez-le en 5 mots.
- Commencez par une analogie du quotidien (cuisine, bureau de poste, etc.), puis une phrase sur l'endroit où l'analogie ne marche plus.
- Donnez ensuite un exemple concret avec de vraies valeurs.
- Terminez par : « La seule chose à retenir : ... » (une phrase).
- Posez-moi ensuite 2 questions pour vérifier que j'ai compris, et attendez. Ne répondez pas à ma place.
  Quand je réponds, corrigez chaque réponse en 1 à 2 phrases.

🖼️ Apprendre avec un schéma

À utiliser quand un sujet, un problème ou un processus est difficile à comprendre. L'agent crée une seule page HTML avec un schéma.

À remplir : [SUJET / PROBLÈME / PROCESSUS] [PUBLIC]

Apprenez-moi [SUJET / PROBLÈME / PROCESSUS] sous forme d'une seule page HTML autonome.
L'objectif est la compréhension, pas la décoration.

D'abord : si le sujet ou le public n'est pas clair, posez-moi jusqu'à 3 questions et attendez.

Public : [PUBLIC : diplômé | développeur junior | non technique].
Expliquez la chose elle-même, avec des mots simples, à ce niveau.
Définissez chaque terme que ce public peut ne pas connaître, la première fois qu'il apparaît,
en moins de 8 mots. Ne définissez pas les termes qu'il connaît déjà.

Structure de la page, dans cet ordre :
1. Titre, puis une réponse en une phrase : ce que c'est, ou quel est le problème.
2. Pourquoi c'est important : une phrase sur ce qui se passe mal sans cela.
3. Le schéma (partie principale). 10 cases maximum, libellés de 4 mots maximum.
   - Numérotez les étapes 1, 2, 3 dans l'ordre de lecture.
   - Une couleur par acteur ou composant, avec une petite légende.
     Les décisions sont des losanges ; les boucles sont des flèches qui reviennent en arrière.
   - Sous le schéma, une phrase simple par étape numérotée : ce qui se passe et pourquoi.
4. Un exemple détaillé avec de vraies valeurs, parcouru étape par étape.
   Si ce projet a un cas réel, utilisez-le.
5. Erreurs fréquentes : 3 puces maximum.
6. « À retenir » : une phrase.

Règles techniques :
- UN seul fichier, avec un <style> intégré. Pas de ressource externe, pas de CDN, pas de framework ;
  fonctionne hors ligne depuis file://.
- Placez les cases du schéma avec CSS grid ; gardez les flèches simples (CSS ou petites
  lignes SVG). Rien ne doit se chevaucher, et aucun texte ne doit dépasser de sa case.
  Si vous pouvez ouvrir la page dans un navigateur, vérifiez-le avant de finir.
- Sous 600 px de large, le schéma se place en colonne, de haut en bas. Lisible à l'impression.
- Couleurs en variables CSS dans :root.
- Phrases courtes. Pas de remplissage. Rien en dehors de la structure ci-dessus.

Enregistrez sous [nom-du-sujet].html.

🗺️ Me faire visiter ce dépôt

À utiliser quand vous ouvrez un projet que vous ne connaissez pas encore. L'agent lit le code (sans rien modifier) et vous donne une carte, un exemple réel, et les fichiers à lire en premier.

À remplir : [ZONE]

Faites-moi visiter [ZONE, ou « tout le dépôt »] de ce dépôt. Je suis nouveau ici. Lecture seule : ne modifiez rien.

1. En 3 phrases : ce que fait ce projet et qui l'utilise.
2. La stack : langage, framework, et comment le lancer et lancer ses tests.
3. La carte : 8 dossiers ou modules principaux au maximum, une ligne sur ce que chacun gère.
4. Un exemple réel : prenez une action courante (un clic, une requête, une commande)
   et suivez-la étape par étape dans le code, avec les chemins de fichiers.
5. Les 3 pièges principaux : ce qui me surprendrait avant ma première modification.
6. À lire ensuite : les 5 fichiers à lire en premier, dans l'ordre, avec une ligne sur la raison.

Règles :
- 80 lignes maximum.
- Mots simples, phrases courtes. Définissez tout terme qu'un développeur junior ne connaît peut-être pas.
- Pointez vers de vrais fichiers (path:line). Ne devinez pas : si vous n'êtes pas sûr, dites-le.
- Ensuite, demandez-moi ce que je veux changer, et attendez.
✍️

Laissez l'agent écrire le prompt

Pour une grosse tâche, n'écrivez pas le prompt vous-même. Donnez les éléments à l'agent (objectif, contexte, règles, quand c'est fini) et demandez-lui d'écrire le vrai prompt.

📝 Comme expliquer à un ami ce dont vous avez besoin : il rédige l'e-mail pour vous. Vous le relisez quand même avant de l'envoyer.

✍️ Écrivez-moi un prompt

À utiliser quand une tâche est grosse ou que vous allez réutiliser le prompt. Relisez le résultat, corrigez-le, puis collez-le dans une nouvelle session.

À remplir : [OBJECTIF] [CONTEXTE] [À FAIRE] [À NE PAS FAIRE] [FINI QUAND]

Écrivez un prompt pour un agent de code. Ne faites pas la tâche vous-même.

Objectif : [OBJECTIF]
Contexte : [CONTEXTE : projet, fichiers, pour qui]
À faire : [À FAIRE]
À ne pas faire : [À NE PAS FAIRE]
Fini quand : [FINI QUAND]

D'abord : lisez les fichiers dont vous avez besoin. Puis posez-moi jusqu'à 5 questions,
uniquement sur ce que le code ne peut pas vous dire, et attendez.

Ensuite, écrivez le prompt :
- Pour un agent qui n'a aucune mémoire de cette discussion : mettez tout ce dont il a besoin.
- Des étapes claires, dans l'ordre. Phrases courtes, mots simples.
- Dites où s'arrêter pour me demander, et quoi me rendre à la fin.
- Mettez [ENTRE CROCHETS] ce que je dois remplir à chaque fois.
- 40 lignes max. Enlevez ce que l'agent ferait de toute façon.

Listez 3 façons dont il pourrait mal tourner, corrigez le prompt pour chacune, puis montrez-le dans un seul bloc de code.
💡

Astuce : l'agent est bon pour la structure, vous connaissez l'objectif. Relisez toujours le prompt qu'il écrit : s'il contient une erreur, l'agent la refera à chaque fois.
