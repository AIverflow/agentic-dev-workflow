Prompts prêts à l'emploi

Copiez un prompt, remplissez les trous, puis collez-le dans une nouvelle session d'agent.

🧒 Expliquer simplement (ELI5)

À utiliser quand un sujet semble difficile. L'agent l'explique avec des mots simples, puis vérifie que vous avez compris.

À remplir : [SUJET]

Expliquez [SUJET] à un débutant complet, comme si j'avais 5 ans.
- 150 mots maximum (sans compter les questions). Phrases courtes. Pas de jargon ; si un terme est inévitable, définissez-le en 5 mots.
- Commencez par une analogie du quotidien (cuisine, bureau de poste, etc.), puis une phrase sur l'endroit où l'analogie ne marche plus.
- Donnez ensuite un exemple concret avec de vraies valeurs.
- Terminez par : « La seule chose à retenir : ... » (une phrase).
- Posez-moi ensuite 2 questions pour vérifier que j'ai compris, et attendez. Ne répondez pas à ma place.
  Quand je réponds, corrigez chaque réponse en 1 à 2 phrases.

🖼️ Apprendre avec un schéma

À utiliser quand un sujet, un problème ou un processus est difficile à comprendre. L'agent crée une seule page HTML avec un schéma.

À remplir : [SUJET / PROBLÈME / PROCESSUS] [PUBLIC]

Apprenez-moi [SUJET / PROBLÈME / PROCESSUS] sous forme d'une seule page HTML autonome.
L'objectif est la compréhension, pas la décoration.

D'abord : si le sujet ou le public n'est pas clair, posez-moi jusqu'à 3 questions et attendez.

Public : [diplômé | développeur junior | non technique].
Expliquez la chose elle-même, avec des mots simples, à ce niveau.
Définissez chaque terme que ce public peut ne pas connaître, la première fois qu'il apparaît,
en moins de 8 mots. Ne définissez pas les termes qu'il connaît déjà.

Structure de la page, dans cet ordre :
1. Titre, puis une réponse en une phrase : ce que c'est, ou quel est le problème.
2. Pourquoi c'est important : une phrase sur ce qui se passe mal sans cela.
3. Le schéma (partie principale). 10 cases maximum, libellés de 4 mots maximum.
   - Numérotez les étapes 1, 2, 3 dans l'ordre de lecture.
   - Une couleur par acteur ou composant, avec une petite légende.
     Les décisions sont des losanges ; les boucles sont des flèches qui reviennent en arrière.
   - Sous le schéma, une phrase simple par étape numérotée : ce qui se passe et pourquoi.
4. Un exemple détaillé avec de vraies valeurs, parcouru étape par étape.
5. Erreurs fréquentes : 3 puces maximum.
6. « À retenir » : une phrase.

Règles techniques :
- UN seul fichier, avec un <style> intégré. Pas de ressource externe, pas de CDN, pas de framework ;
  fonctionne hors ligne depuis file://.
- Placez les cases du schéma avec CSS grid ; gardez les flèches simples (CSS ou petites lignes SVG). Rien ne doit se chevaucher, et aucun texte ne doit dépasser de sa case.
  Si vous pouvez ouvrir la page dans un navigateur, vérifiez-le avant de finir.
- Sous 600 px de large, le schéma se place en colonne, de haut en bas. Lisible à l'impression.
- Couleurs en variables CSS dans :root.
- Phrases courtes. Pas de remplissage. Rien en dehors de la structure ci-dessus.

Enregistrez sous [nom-du-sujet].html.

🗺️ Me faire visiter ce dépôt

À utiliser quand vous ouvrez un projet que vous ne connaissez pas encore. L'agent lit le code (sans rien modifier) et vous donne une carte, un exemple réel, et les fichiers à lire en premier.

À remplir : [ZONE]

Faites-moi visiter [ZONE] de ce dépôt. Je suis nouveau ici. Lecture seule : ne modifiez rien.

1. En 3 phrases : ce que fait ce projet et qui l'utilise.
2. La stack : langage, framework, et comment le lancer et lancer ses tests.
3. La carte : 8 dossiers ou modules principaux au maximum, une ligne sur ce que chacun gère.
4. Un exemple réel : prenez une action courante (un clic, une requête, une commande)
   et suivez-la étape par étape dans le code, avec les chemins de fichiers.
5. Les 3 pièges principaux : ce qui me surprendrait avant ma première modification.
6. À lire ensuite : les 5 fichiers à lire en premier, dans l'ordre, avec une ligne sur la raison.

Règles :
- Mots simples, phrases courtes. Définissez tout terme qu'un développeur junior ne connaît peut-être pas.
- Pointez vers de vrais fichiers (path:line). Ne devinez pas : si vous n'êtes pas sûr, dites-le.
- Ensuite, demandez-moi ce que je veux changer, et attendez.

📦 Passer le relais à une session neuve

À utiliser quand la session devient longue, que l'agent commence à oublier des choses, ou qu'une étape est finie. L'agent écrit une courte note, puis une nouvelle session la lit et continue.

Rien à remplir. Dans la nouvelle session, dites : Lisez handoff.md et continuez.

Nous arrêtons cette session. Écrivez une note de passation pour qu'un nouvel agent, sans mémoire
de cette discussion, puisse continuer le travail. Enregistrez-la sous handoff.md.

Sections, dans cet ordre :
1. Objectif : ce que nous construisons, en 2 phrases.
2. Décisions : ce que nous avons choisi, et pourquoi, une ligne chacune.
   Indiquez aussi les options rejetées, pour que personne ne les rouvre.
3. Fait : ce qui est terminé et fonctionne (avec les chemins de fichiers).
4. Pas fait : ce qui reste, dans l'ordre, la plus petite prochaine étape en premier.
5. Questions ouvertes : tout ce que je dois encore décider.
6. Attention : les pièges rencontrés, et les choses qui semblaient justes mais étaient fausses.
7. À lire en premier : les fichiers que le nouvel agent doit ouvrir, avec une ligne sur la raison.

Règles :
- 60 lignes maximum. Des faits seulement, pas le récit de la discussion.
- Pointez vers des fichiers et des commits, ne collez pas de code.
- Ne changez aucun code maintenant.
- Montrez-moi la note une fois finie, pour que je puisse la corriger avant de changer de session.

🎟️ Construire des tickets en parallèle

À utiliser pour construire plusieurs tickets à la fois. Un agent orchestrateur planifie, relit et fait les commits, et des agents auxiliaires écrivent le code.

À remplir : Tickets Branche de base Tickets max en parallèle

Vous êtes l'**orchestrateur** pour construire un ensemble de tickets.
Vous planifiez, distribuez le travail, relisez et faites les commits. Des sous-agents auxiliaires écrivent le code.

## Entrées (à remplir)

- **Tickets :** <chemin vers un dossier ou une spec, numéros ou URL d'issues, ou une liste collée>
- **Branche de base :** <par ex. main>
- **Tickets max en parallèle :** <par défaut 3>

## Règles de base

- C'est moi qui décide. Ne devinez jamais une question de produit ou de design : demandez-moi.
- Suivez le `AGENTS.md` / `CLAUDE.md` du dépôt, les standards de code et les conventions de commit.
- Donnez aux auxiliaires des **pointeurs**, pas des copies : chemin ou URL du ticket, chemin de la spec, fichiers concernés.
- Ne poussez pas, n'ouvrez pas de PR et ne fermez pas de tickets sauf si je le dis.
- Tout le monde travaille dans le même dossier, sur une seule branche. Deux tickets tournent en même temps seulement s'ils touchent des **fichiers différents**. Sinon, faites-les l'un après l'autre.
- Si vous ne pouvez pas lancer des sous-agents en parallèle, faites les tickets un par un.

## Étape 1 : planifier, puis attendre mon accord

1. Lisez chaque ticket, sa spec, et le glossaire et les standards de code du dépôt, s'ils existent.
2. Trouvez les commandes pour la vérification des types, le lint, un seul fichier de test, et toute la suite de tests.
3. Montrez-moi :
   - un tableau : ticket, bloqué par (marquez les suppositions « déduit »), fichiers qu'il touchera probablement
   - le premier lot : les tickets sans blocage ouvert et sans fichiers communs
   - les questions ouvertes, chacune avec votre réponse recommandée
4. Créez la branche `tickets/<nom-court>` à partir de la branche de base.
5. **Arrêtez-vous. Attendez mon accord et mes réponses.**

## Étape 2 : la boucle, pour chaque ticket

1. **Construire** (sous-agent implémenteur) :
   - Test d'abord : un test qui échoue pour un petit comportement, puis juste assez de code pour le faire passer. Répétez. Utilisez le skill `tdd` s'il est installé.
   - Ne modifiez que les fichiers prévus pour ce ticket. S'il en faut un autre, arrêtez-vous et demandez à l'orchestrateur.
   - Restez dans le périmètre du ticket. Pas de refactor parasite. Ne faites pas de commit.
   - Question bloquante (exigence floue, deux conceptions valables, périmètre qui doit grandir) ? Arrêtez-vous et signalez-la avec les options et une recommandation. Ne devinez pas.
   - Rapport : fichiers modifiés, résultats des tests, doutes.
2. **Relire** (un sous-agent relecteur séparé, jamais l'implémenteur) :
   - Lisez le ticket et le diff de ses fichiers. Utilisez le skill `code-review` s'il est installé.
   - **Spec** : fait-il tout ce que demande le ticket, et rien de plus ?
   - **Standards** : suit-il les règles du dépôt ? Est-il simple et clair ?
   - Rapportez les constats, du plus important au moins important. Ne corrigez rien.
3. **Corriger** : renvoyez les constats à l'implémenteur. **2 tours de correction maximum**, puis demandez-moi.
4. **Commit** : lancez toute la suite de tests. Si elle passe, commitez seulement les fichiers de ce ticket, avec un message qui nomme le ticket. Si elle échoue, renvoyez à l'étape 1.
5. **Suite** : marquez le ticket comme terminé (pour des fichiers locaux, mettez `Status: done`), puis lancez les tickets qui sont maintenant débloqués.

### Quand me demander

- Un ticket bloqué attend ; les autres continuent. Envoyez-moi les questions **en un seul lot** : ticket, question, options, votre recommandation.
- Tout arrêter et me demander si les tests restent rouges après un nouvel essai, si un ticket échoue deux fois à la relecture, ou si deux tickets se contredisent.
- Après chaque commit, envoyez une ligne d'état : terminé, en cours, bloqué.

## Étape 3 : finir

1. Lancez une dernière fois toute la suite de tests et la vérification des types.
2. Relisez toute la branche par rapport à la branche de base (Spec et Standards).
3. Corrigez ce que nous avons convenu de corriger.
4. Rapportez un tableau : ticket, tests, constats de relecture, tours de correction, questions posées. Listez ce qui mérite un ticket de suivi.
5. Laissez la branche prête pour que je la relise et la fusionne.

Laissez l'agent écrire le prompt

Pour une grosse tâche, n'écrivez pas le prompt vous-même. Donnez les éléments à l'agent (objectif, contexte, règles, quand c'est fini) et demandez-lui d'écrire le vrai prompt.

📝 Comme expliquer à un ami ce dont vous avez besoin : il rédige l'e-mail pour vous. Vous le relisez quand même avant de l'envoyer.

✍️ Écrivez-moi un prompt

À utiliser quand une tâche est grosse ou que vous allez réutiliser le prompt. Relisez le résultat, corrigez-le, puis collez-le dans une nouvelle session.

À remplir : [OBJECTIF] [CONTEXTE] [À FAIRE] [À NE PAS FAIRE] [FINI QUAND]

Écrivez un prompt pour un agent de code. Ne faites pas la tâche vous-même.

Objectif : [OBJECTIF]
Contexte : [CONTEXTE : projet, fichiers, pour qui]
À faire : [À FAIRE]
À ne pas faire : [À NE PAS FAIRE]
Fini quand : [FINI QUAND]

D'abord : posez-moi jusqu'à 5 questions sur ce qui manque ou n'est pas clair, et attendez.

Ensuite, écrivez le prompt :
- Pour un agent qui n'a aucune mémoire de cette discussion : mettez tout ce dont il a besoin.
- Des étapes claires, dans l'ordre. Phrases courtes, mots simples.
- Dites où s'arrêter pour me demander, et quoi me rendre à la fin.
- Mettez [ENTRE CROCHETS] ce que je dois remplir à chaque fois.
- 40 lignes max. Enlevez ce que l'agent ferait de toute façon.

Montrez-le dans un seul bloc de code, puis listez 3 façons dont il pourrait mal tourner.
💡

Astuce : l'agent est bon pour la structure, vous connaissez l'objectif. Relisez toujours le prompt qu'il écrit : s'il contient une erreur, l'agent la refera à chaque fois.

Basé sur les skills de Matt Pocock pour agents de code. À jour avec la version 1.3.1 (octobre 2026). Dans le menu des commandes, les skills peuvent apparaître avec un préfixe, par exemple /mattpocock-skills:grill-with-docs.
