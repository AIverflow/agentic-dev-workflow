Avant de commencer

Les bases

🤖

Qu'est-ce qu'un agent de code ?

Un assistant IA qui travaille dans le dossier de votre projet. Il lit vos fichiers, écrit du code et lance des commandes, comme un collègue assis à votre ordinateur. Exemples : Claude Code, Codex, Cursor, Hermes Agent.

🧩

Qu'est-ce qu'un skill ?

Une fiche recette que l'agent suit pour une tâche précise. On lance un skill en tapant une barre oblique suivie de son nom, par exemple /grill-with-docs.

🧰

Ce qu'il vous faut

  • Un agent de code, n'importe lequel
  • Un dossier de projet qui utilise git (l'agent y enregistre son travail)
  • C'est tout. Pas de compte GitHub, pas d'éditeur spécial.

Un mot que vous ne connaissez pas ? Voyez le Vocabulaire à la fin, ou demandez à votre agent.

⚙️ Installation : une fois par projet, environ 5 minutes

Ça transforme un projet normal en un projet où votre agent travaille bien. Marche sur un projet neuf ou existant.

1

Installer les skills (une fois par ordinateur)

Demandez simplement à votre agent de code :

Installe les skills de Matt Pocock depuis github.com/mattpocock/skills

Les skills n'apparaissent pas dans le menu des commandes ? Redémarrez votre agent.

2

Donner un guide du projet à l'agent : /init

La plupart des agents ont une commande init. L'agent parcourt votre projet et écrit un fichier guide (CLAUDE.md ou AGENTS.md, selon l'agent) : comment lancer, tester et construire le projet, et où se trouvent les choses. L'agent le lit au début de chaque session.

Ce code est nouveau pour vous aussi ? Le prompt Me faire visiter ce dépôt vous donne d'abord une carte.

3

Brancher les skills : /setup-matt-pocock-skills

Pose 2–3 questions, puis ajoute une section « Agent skills » à votre guide et écrit quelques petits fichiers de config dans docs/agents/.

Quand il demande où ranger les tickets, choisissez fichiers locaux.

Introuvable ? Tapez le nom complet : /mattpocock-skills:setup-matt-pocock-skills. Pareil pour chaque skill.

✅ C'est prêt. Votre projet est paré pour les 5 étapes ci-dessous.

💡 Pourquoi suivre un workflow ?

La raison n°1 pour laquelle le code avec l'IA tourne mal : l'agent construit quelque chose, mais pas ce que vous vouliez. La solution : ralentir au début. On se met d'accord sur l'idée, on l'écrit, on la découpe en petits morceaux, et seulement ensuite on code.

Pensez à la construction d'une maison : 🗣️ discussion avec l'architecte → 📐 plan → 📋 bons de travaux → 🧱 construction, avec des contrôles en cours de route → 🔍 inspection finale.

🩹 Petite modification ? Passez directement à la suite.

Une faute de frappe, une correction d'une ligne, un petit changement de couleur : pas besoin de cinq étapes. Demandez simplement à l'agent, ou tapez /tdd pour une correction rapide en testant d'abord.

Utilisez le workflow complet quand il y a des choix à faire, que le changement touche plusieurs fichiers, ou qu'il prend plus d'une session.

📌 Notre exemple du début à la fin : quelqu'un vole des repas dans le frigo du bureau, encore et encore. On construit une petite app de frigo pour étiqueter son repas, signaler un vol et nommer les principaux suspects.

Étape 1

Grill me (with docs)

/grill-with-docs

L'agent vous interroge avec plein de questions jusqu'à ce que vous soyez d'accord sur ce qu'il faut construire, et note au fur et à mesure le vocabulaire du projet et les grandes décisions.

🏠 Comme un bon architecte qui demande « Combien de chambres ? Grande cuisine ou petite ? » avant de dessiner quoi que ce soit.

Vous
  • Décrivez votre idée en une phrase
  • Répondez à chaque question (des réponses courtes suffisent)
  • Dites « je ne sais pas » quand c'est le cas. L'agent propose une réponse.
Agent
  • Pose les questions par petites séries
  • Propose une réponse recommandée pour chacune
  • Continue jusqu'à ce que plus rien ne soit flou
  • Met à jour le glossaire (GLOSSARY.md) et note les grandes décisions
Exemple
Agent de code : fridge-app
Vous
/grill-with-docs Quelqu'un mange sans arrêt mon repas dans le frigo du bureau. Je veux une app pour l'attraper.
Agent

Q1 : Les signalements de vol doivent-ils être anonymes ? → Je recommande que oui. Personne ne veut d'une guerre du frigo avec son nom dessus.

Q2 : Et si quelqu'un est accusé alors que le yaourt était vraiment à lui ? → Je recommande un bouton « C'était à moi » qui annule le signalement.

Vous
Anonymes, oui. Et ajoute le bouton. Dave en aura besoin.
Agent

Série suivante. Q3 : Un repas peut-il périmer ? Après deux semaines, est-ce encore un repas, ou une expérience scientifique ?…

Ce qu'il écrit en chemin
GLOSSARY.mdRepas : un aliment étiqueté, avec un propriétaire et une date. Signalement : une déclaration anonyme disant que quelqu'un a pris un repas qui n'était pas le sien.

Pourquoi c'est utile : la prochaine fois, vous et l'agent utilisez les mêmes mots pour les mêmes choses. Moins de malentendus, des réponses plus courtes. (/grill-me tout court fait l'interview sans les docs. Pratique pour les sujets hors code.)

💡

Astuce : c'est l'étape que tout le monde saute, et c'est la plus importante. Dix minutes de questions évitent des heures à corriger la mauvaise chose. Perdu devant une question ? Ouvrez une nouvelle fenêtre et collez le prompt Expliquer simplement.

📄
Étape 2

Écrire la spec

/to-spec

L'agent transforme votre conversation en plan écrit (une « spec »). Pas de nouvelles questions, il écrit juste ce que vous avez décidé.

🏠 Le plan de la maison. Tout le monde peut le relire plus tard et vérifier « c'est bien ce qu'on avait dit ? »

Vous
  • Lancez-le juste après l'interview, dans la même conversation
  • Validez comment l'agent compte tester la fonctionnalité
  • Lisez la spec. Corrigez ce qui ne va pas.
Agent
  • Parcourt votre code
  • Liste ce qui est hors périmètre
Exemple : ce que l'agent écrit
.scratch/fridge-thief/spec.md## Problème Des repas disparaissent sans arrêt du frigo du bureau. Personne ne sait qui. ## Solution Étiqueter son repas. Signaler un vol, de façon anonyme. Un tableau « Most wanted » affiche les principaux suspects. ## User stories 1. En tant que collègue, je veux étiqueter mon repas avec mon nom et la date… 2. En tant que victime, je veux signaler un repas volé sans donner mon nom… 3. En tant que collègue accusé, je veux dire « c'était à moi »… 4. En tant que n'importe qui, je veux voir le tableau « Most wanted »… ## Hors périmètre Caméras dans le frigo, relevé d'empreintes sur le yaourt.
💡

Astuce : la spec, c'est votre document. Si quelque chose cloche, dites-le maintenant. Corriger une phrase coûte bien moins cher que corriger du code.

🎟️
Étape 3

Découper en tickets

/to-tickets

L'agent découpe la spec en petits tickets. Chacun est un petit morceau qui fonctionne tout seul.

🏠 Les bons de travaux : « plomberie de la cuisine », « électricité de la chambre ». Une équipe, une tâche, une journée.

✅ Bien : des parts

01
02
03

Chaque ticket traverse toutes les couches (écran, logique, sauvegarde) pour une petite fonctionnalité. On peut l'essayer dès qu'il est fini.

❌ Mal : des étages

tous les écrans
toute la logique
toute la sauvegarde

« D'abord tous les écrans, puis toute la logique… » Rien ne marche avant la toute fin.

Vous
  • Vérifiez la liste proposée
  • Trop gros ? Trop petit ? Demandez de découper ou de fusionner.
  • Validez
Agent
  • Propose les tickets, dans l'ordre
  • Indique quel ticket doit attendre lequel
  • Enregistre un fichier par ticket
Exemple : les tickets de l'app de frigo
01
Étiqueter son repas
Attend : rien, on peut commencer
02
Signaler un repas volé, avec un bouton « C'était à moi »
Attend : 01
03
Tableau « Most wanted »
Attend : 02

Enregistrés sous .scratch/fridge-thief/issues/01-label-lunch.md, 02-…, 03-…

💡

Astuce : chaque ticket est taillé pour tenir dans une session neuve de l'agent. Des petits tickets, c'est un agent concentré qui fait moins d'erreurs.

🛠️
Étape 4

Coder, en testant d'abord (TDD)

/implement

L'agent réalise un ticket en écrivant d'abord le test, puis le code qui le fait passer.

🏠 Avant de monter un mur, on écrit le contrôle : « le mur doit être droit ». On construit. On contrôle. Mur suivant.

La boucle TDD (développement piloté par les tests)

🔴 RougeÉcrire un test pour un petit comportement.
Il échoue, car le code n'existe pas encore.
→
🟢 VertÉcrire juste assez de code
pour que le test passe.
↻
RecommencerComportement suivant,
jusqu'à la fin du ticket.

Pourquoi ? Les tests donnent à l'agent une preuve que son code marche, au lieu de simplement y croire. Sans tests, il avance à l'aveugle.

Vous
  • Ouvrez une session neuve (/clear, /new ou une nouvelle conversation). Vos fichiers restent ; le ticket dit à l'agent ce dont il a besoin.
  • Indiquez un ticket à l'agent
  • Validez ce qui sera testé
  • Observez, et intervenez s'il part dans la mauvaise direction
Agent
  • Enchaîne la boucle rouge → vert
  • Lance tous les tests à la fin
  • Lance la revue (étape 5) tout seul
  • Puis enregistre le travail (commit git)
Exemple
Agent de code : fridge-app (session neuve)
Vous
/clear
/implement .scratch/fridge-thief/issues/01-label-lunch.md
Agent

🔴 Test : « un repas étiqueté affiche le nom de son propriétaire ». Échoue, comme prévu.

🟢 Ajouté le formulaire d'étiquette et la liste des repas. Le test passe.

🔴 Test : « un repas sans nom ne peut pas être enregistré »… 🟢 passe.

✅ Tous les tests passent. Je lance la revue… puis je fais le commit.

⚡ Option rapide : tous les tickets d'un coup avec /implement-spec

Au lieu d'un ticket par session, l'agent lance plusieurs agents assistants en parallèle. Chacun travaille dans sa propre copie du projet, un ticket chacun, en testant d'abord. Quand un ticket est fini, son travail est fusionné. Les tickets en attente démarrent dès que ceux qui les bloquaient sont finis. À la fin, une seule revue de l'ensemble.

Idéal quand il y a beaucoup de tickets. Commencez par /implement, un ticket à la fois, jusqu'à ce que le workflow vous soit familier. C'est plus facile à suivre et à piloter.

💡

Astuce : la session devient longue, ou l'agent oublie des choses ? Tapez /handoff : l'agent écrit une courte note pour la session suivante. Puis /clear et reprenez à neuf.

🔍
Étape 5

Revue de code

/code-review

L'agent vérifie le travail : le code est-il propre, et fait-il ce que le ticket demandait, rien de plus ?

🏠 L'inspection finale : construit aux normes, et conforme au plan.

Vous
  • Essayez la fonctionnalité vous-même
  • Lisez le rapport
  • Décidez quoi corriger : « corrige 1, ignore 2 »
Agent
  • Signale les problèmes, sans rien corriger de lui-même
  • Corrige ce que vous choisissez
Exemple : rapport de revue
## Revue (2 points) 1. Nom peu clair : la variable `l` devrait s'appeler `lunch`. 2. En trop : ajout d'un envoi de photo de « caméra de frigo ». La spec dit que c'est hors périmètre.
🔁

Ticket suivant ? Retour à l'étape 4.

Session neuve → /implement ticket 02 → revue → ticket 03… jusqu'à ce que tous les tickets soient faits. 🎉

Autres skills

/ask-matt

Perdu ? Il vous dit quel skill correspond à votre situation.

/diagnosing-bugs

Un bug que vous ne comprenez pas : on le reproduit d'abord, puis on cherche la cause.

/prototype

Un doute sur une conception ? Construisez d'abord une version jetable.

La dernière réponse de l'agent n'avait aucun sens ? Il la réexplique, autrement.

Après une fonctionnalité : l'agent propose des changements à sa propre configuration, pour que la suivante se passe mieux.

Une ligne chacun

Vocabulaire

Contexte
Ce dont l'agent se souvient dans la session en cours. Quand il est plein, l'agent devient moins bon.
Session neuve
Une nouvelle conversation au contexte vide. Vos fichiers ne changent pas.
Guide du projet
Un fichier (AGENTS.md ou CLAUDE.md) que l'agent lit au début de chaque session.
Spec
Le plan écrit : ce qu'il faut construire, et ce qu'il ne faut pas construire.
Hors périmètre
Ce que vous avez décidé de ne pas construire cette fois.
Ticket
Un petit morceau de la spec qui fonctionne tout seul.
Test
Un bout de code qui vérifie qu'un autre bout de code fait ce qu'il doit.
TDD
Développement piloté par les tests : écrire le test d'abord, le voir échouer, puis écrire le code.
Commit
Un instantané enregistré du projet dans git. Vous pouvez toujours y revenir.
