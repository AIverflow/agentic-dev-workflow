Die Grundlagen

🤖

Was ist ein Coding-Agent?

Ein KI-Assistent, der direkt in deinem Projektordner arbeitet. Er kann deine Dateien lesen, Code schreiben und Befehle ausführen, wie ein Kollege, der an deinem Rechner sitzt. Beispiele: Claude Code, Codex, Cursor.

🧩

Was ist ein Skill?

Eine Rezeptkarte, der der Agent für eine bestimmte Aufgabe folgt. Du startest einen Skill, indem du einen Schrägstrich und seinen Namen tippst, zum Beispiel /grill-with-docs.

⚙️ Einrichtung: einmal pro Projekt, etwa 5 Minuten

Damit wird ein normales Projekt zu einem, in dem dein Agent gut arbeiten kann. Funktioniert bei einem neuen oder bestehenden Projekt.

1

Skills installieren (einmal pro Rechner)

Bitte einfach deinen Agenten:

Installiere die Skills von Matt Pocock (mattpocock-skills, aus dem offiziellen Claude-Plugin-Marketplace).

Funktioniert mit den meisten Coding-Agenten. Quelle: github.com/mattpocock/skills

2

Gib deinem Agenten einen Projektleitfaden: /init

Die meisten Coding-Agenten haben einen init-Befehl. Der Agent durchsucht dein Projekt und schreibt eine Leitfaden-Datei (CLAUDE.md oder AGENTS.md, je nach Agent): wie man es startet, testet und baut, und wo was liegt. Der Agent liest sie zu Beginn jeder Sitzung.

3

Skills anbinden: /setup-matt-pocock-skills

Stellt 2–3 Fragen, fügt dann einen Abschnitt „Agent skills" zu deinem Leitfaden hinzu und schreibt ein paar kleine Konfigurationsdateien in docs/agents/.

Wenn gefragt wird, wo Tickets gespeichert werden, wähle lokale Dateien. Kein GitHub-Konto nötig.

✅ Fertig. Dein Projekt ist bereit für die 6 Schritte unten.

💡 Warum überhaupt einem Workflow folgen?

Der häufigste Grund, warum Programmieren mit KI schiefgeht: Der Agent baut etwas, aber nicht das, was du gemeint hast. Die Lösung: am Anfang langsamer machen. Erst über die Idee einig werden, sie aufschreiben, in kleine Teile schneiden, und erst dann Code schreiben.

Denk an einen Hausbau: 🗣️ Gespräch mit dem Architekten → 📐 Bauplan → 📋 Arbeitsaufträge → 🧱 Bau, mit Kontrollen unterwegs → 🔍 Endabnahme → 🪞 Team-Nachbesprechung.

🔥 Grill with docs→ 📄 Spec→ 🎟️ Tickets→ 🛠️ Code + TDD→ 🔍 Review→ 🪞 Retro

📌 Unser Beispiel von Anfang bis Ende: einen Dark Mode zu einer einfachen To-do-App hinzufügen.

🔥
Schritt 1

Grill me (with docs)

/grill-with-docs

Der Agent befragt dich mit vielen Fragen, bis ihr euch einig seid, was genau gebaut wird, und schreibt dabei die Begriffe und großen Entscheidungen des Projekts auf.

🏠 Wie ein guter Architekt, der fragt „Wie viele Schlafzimmer? Große oder kleine Küche?", bevor er irgendetwas zeichnet.

Du
  • Beschreibe deine Idee in einem Satz
  • Beantworte jede Frage (kurze Antworten reichen)
  • Sag „weiß ich nicht", wenn du es nicht weißt. Der Agent schlägt eine Antwort vor.
Agent
  • Fragt in kleinen Runden
  • Gibt zu jeder Frage eine empfohlene Antwort
  • Macht weiter, bis nichts mehr unklar ist
  • Aktualisiert das Glossar (GLOSSARY.md) und die Entscheidungsnotizen (docs/adr/)
Beispiel
Coding-Agent: todo-app
Du
/grill-with-docs Ich möchte meiner To-do-App einen Dark Mode hinzufügen
Agent

F1: Soll er der Hell/Dunkel-Einstellung des Rechners folgen oder einen Umschalter nutzen? → Ich empfehle beides: standardmäßig dem Rechner folgen, mit einem Knopf zum Umschalten.

F2: Soll sich die App deine Wahl nach dem Neuladen merken? → Ja.

Du
Beides, ja. Und ja, merken.
Agent

Nächste Runde. F3: Wo soll der Knopf hin?…

Was er nebenbei schreibt
GLOSSARY.mdTheme: das Farbschema der App, „hell" oder „dunkel". System-Theme: die Hell/Dunkel-Einstellung des Rechners der Nutzerin oder des Nutzers.

Warum das wichtig ist: Beim nächsten Mal benutzt ihr dieselben Wörter für dieselben Dinge. Weniger Missverständnisse, kürzere Antworten. (Das einfache /grill-me macht die Befragung ohne die Dokumente. Praktisch für Themen ohne Code.)

💡

Tipp: Diesen Schritt lassen viele aus, und er ist der wichtigste. Zehn Minuten Fragen sparen Stunden, in denen das Falsche repariert wird. Nutze ihn jedes Mal.

📄
Schritt 2

Die Spec schreiben

/to-spec

Der Agent macht aus eurem Gespräch einen schriftlichen Plan (eine „Spec"). Keine neuen Fragen: Er schreibt nur auf, was ihr vereinbart habt.

🏠 Der Bauplan. Alle können später nachsehen und prüfen: „Ist das, was wir besprochen haben?"

Du
  • Starte ihn direkt nach der Befragung, im selben Chat
  • Bestätige, wie der Agent die Funktion testen will
  • Lies die Spec. Korrigiere, was falsch ist.
Agent
  • Sieht sich deinen Code an
  • Schreibt die Spec in eine Datei
  • Listet auch auf, was nicht dazugehört
Beispiel: was der Agent schreibt
.scratch/dark-mode/spec.md## Problem Die App ist nachts zu hell. ## Lösung Ein dunkles Theme, das der Rechnereinstellung folgt, mit einem Umschaltknopf. ## User Stories 1. Als Nutzer möchte ich die App dunkel, wenn mein Rechner im Dark Mode ist… 2. Als Nutzer möchte ich einen Knopf, um das Theme zu wechseln… 3. Als Nutzer möchte ich, dass meine Wahl nach dem Neuladen erhalten bleibt… ## Nicht im Umfang Eigene Farben, automatischer Dark Mode bei Sonnenuntergang.
💡

Tipp: Die Spec ist dein Dokument. Wenn etwas nicht stimmt, sag es jetzt. Einen Satz zu korrigieren ist viel billiger, als Code zu korrigieren.

🎟️
Schritt 3

In Tickets schneiden

/to-tickets

Der Agent teilt die Spec in kleine Tickets auf. Jedes ist ein kleines Stück, das für sich allein funktioniert.

🏠 Arbeitsaufträge: „Sanitär für die Küche", „Elektrik fürs Schlafzimmer". Ein Team, eine Aufgabe, ein Tag.

✅ Gut: Stücke

01
02
03

Jedes Ticket geht durch alle Schichten (Oberfläche, Logik, Speichern) für eine kleine Funktion. Du kannst es ausprobieren, sobald es fertig ist.

❌ Schlecht: Schichten

alle Oberflächen
die ganze Logik
das ganze Speichern

„Erst alle Oberflächen, dann die ganze Logik…" Bis ganz zum Schluss funktioniert nichts.

Du
  • Prüfe die vorgeschlagene Liste
  • Zu groß? Zu klein? Lass teilen oder zusammenlegen.
  • Gib frei
Agent
  • Schlägt die Tickets vor, in Reihenfolge
  • Sagt, welches Ticket auf welches warten muss
  • Speichert eine Datei pro Ticket
Beispiel: die Tickets für den Dark Mode
01
Ein Knopf wechselt das Theme
Wartet auf: nichts, sofort starten
02
Wahl nach dem Neuladen merken
Wartet auf: 01
03
Standardmäßig der Rechnereinstellung folgen
Wartet auf: 01

Gespeichert als .scratch/dark-mode/issues/01-toggle-button.md, 02-…, 03-…

💡

Tipp: Jedes Ticket ist so bemessen, dass es in eine frische Agent-Sitzung passt. Kleine Tickets = ein fokussierter Agent, der weniger Fehler macht.

🛠️
Schritt 4

Bauen, Test zuerst (TDD)

/implement

Der Agent baut ein Ticket und schreibt dabei zuerst den Test, dann den Code, der ihn bestehen lässt.

🏠 Bevor eine Wand gebaut wird, schreibt man die Prüfung auf: „Die Wand muss gerade sein." Bauen. Prüfen. Nächste Wand.

Die TDD-Schleife (testgetriebene Entwicklung)

🔴 RotSchreibe einen Test für ein kleines Verhalten.
Er schlägt fehl, weil der Code noch nicht existiert.
→
🟢 GrünSchreibe gerade genug Code,
damit der Test besteht.
↻
WiederholenNächstes kleines Verhalten,
bis das Ticket fertig ist.

Warum? Tests geben dem Agenten einen Beweis, dass sein Code funktioniert, statt es nur zu glauben. Ohne Tests tappt er im Dunkeln.

Du
  • Starte eine frische Sitzung (/clear oder ein neuer Chat)
  • Gib dem Agenten ein Ticket
  • Vereinbart, was getestet wird
  • Schau zu, und greif ein, wenn er vom Weg abkommt
Agent
  • Durchläuft die Schleife Rot → Grün
  • Lässt am Ende alle Tests laufen
  • Startet das Review (Schritt 5) selbst
  • Sichert die Arbeit (Git-Commit)
Beispiel
Coding-Agent: todo-app (frische Sitzung)
Du
/clear
/implement .scratch/dark-mode/issues/01-toggle-button.md
Agent

🔴 Test: „Klick auf den Theme-Knopf macht die Seite dunkel". Schlägt fehl, wie erwartet.

🟢 Knopf und dunkle Farben hinzugefügt. Test besteht.

🔴 Test: „Zweimal klicken wechselt zurück zu hell"… 🟢 besteht.

✅ Alle Tests bestehen. Committet. Starte das Review…

⚡ Schnellere Option: alle Tickets auf einmal mit /implement-spec

Statt einem Ticket pro Sitzung startet der Agent mehrere Helfer-Agenten parallel. Jeder arbeitet in seiner eigenen Kopie des Projekts, ein Ticket pro Helfer, Test zuerst. Ist ein Ticket fertig, wird seine Arbeit in einen gemeinsamen Branch gemergt. Wartende Tickets starten, sobald ihre Blocker fertig sind. Am Ende gibt es ein Review für alles.

Am besten bei vielen Tickets. Fang mit /implement an, ein Ticket nach dem anderen, bis sich der Ablauf natürlich anfühlt. So ist es leichter zu verfolgen und zu steuern.

💡

Tipp: Du willst auch bei einem schnellen Fix außerhalb dieses Ablaufs zuerst testen? Tippe einfach /tdd. Es ist dieselbe Schleife.

🔍
Schritt 5

Code-Review

/code-review

Zwei getrennte Prüfer sehen sich die Arbeit an. Ist der Code sauber? Und tut er, was das Ticket verlangt?

🏠 Die Endabnahme. Ein Prüfer kontrolliert die Bauvorschriften, ein anderer, ob alles zum Bauplan passt.

📏 Standards

Hält sich der Code an die Regeln des Projekts? Klare Namen? Kein kopierter Code? Nichts unnötig kompliziert?

🎯 Spec

Tut er alles, was das Ticket verlangt, und nicht mehr? Fehlt etwas, ist etwas falsch oder zu viel?

Du
  • Lies beide Berichte
  • Entscheide, was behoben wird: „behebe 1 und 3, ignoriere 2"
Agent
  • Lässt beide Prüfer nebeneinander laufen
  • Meldet Befunde, ohne selbst etwas zu ändern
  • Behebt, was du auswählst
Beispiel: Review-Bericht
## Standards (1 Befund) - Möglicherweise unklarer Name: Variable `t` sollte `theme` heißen. ## Spec (1 Befund) - Zu viel: ein „Sepia"-Theme hinzugefügt, das das Ticket nicht verlangt hat.
💡

Tipp: /implement startet das Review am Ende für dich. Um es selbst zu starten, gib einen Startpunkt an, zum Beispiel /code-review main (alles seit dem main-Branch).

🔁

Nächstes Ticket? Zurück zu Schritt 4.

Frische Sitzung → /implement Ticket 02 → Review → Ticket 03… bis alle Tickets fertig sind. Dann Schritt 6. 🎉

⚡ Viele Tickets? /implement-spec erledigt diese ganze Schleife auf einmal, parallel, mit einem Review am Ende (siehe Schritt 4).

🪞
Schritt 6

Retro: aus der Sitzung lernen

/retro

Der Agent blickt darauf zurück, wie die Arbeit lief, und schlägt vor, wie sich seine eigene Umgebung verbessern lässt, damit das nächste Feature reibungsloser läuft. Er ändert die Umgebung, nicht den Code.

🏠 Die Team-Nachbesprechung, wenn das Haus fertig ist: „Was hat uns gebremst? Was sollten wir nächstes Mal automatisch prüfen?"

Du
  • Starte sie, wenn alle Tickets fertig sind, oder nach einer holprigen Sitzung
  • Wähle, welche Vorschläge umgesetzt werden
Agent
  • Liest die Sitzung noch einmal
  • Findet, was langsam war oder schiefging
  • Schlägt Verbesserungen vor, die wichtigsten zuerst

Worauf sie achtet

🧭

Dinge finden

Hat der Agent Zeit mit der Suche nach Dateien verloren? Einen Hinweis in den Projektleitfaden schreiben.

🚦

Automatische Prüfungen

Hätte ein Linter, ein Test oder eine Prüfung vor dem Commit einen Fehler gefunden? Hinzufügen.

📏

Regeln

Hat das Review etwas übersehen? Eine Regel zu den Coding-Standards hinzufügen, oder eine nutzlose entfernen.

Beispiel
Coding-Agent: todo-app
Du
/retro
Agent

1. Automatische Prüfungen: Ich habe einmal mit einem fehlschlagenden Test committet. Füge eine Prüfung vor dem Commit hinzu, die die Tests ausführt.

2. Dinge finden: Ich habe 6 Dateien nach den Farben durchsucht. Füge eine Zeile in AGENTS.md hinzu: „Die Theme-Farben liegen in styles/theme.css".

Du
Mach beides.
💡

Tipp: Jede Retro macht den Agenten ein bisschen besser in deinem Projekt. Kleine Verbesserungen summieren sich schnell.
