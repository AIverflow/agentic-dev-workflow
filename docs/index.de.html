Die Grundlagen

🤖

Was ist ein Coding-Agent?

Ein KI-Assistent, der direkt in deinem Projektordner arbeitet. Er kann deine Dateien lesen, Code schreiben und Befehle ausführen, wie ein Kollege, der an deinem Rechner sitzt. Beispiele: Claude Code, Codex, Cursor, Hermes Agent.

🧩

Was ist ein Skill?

Eine Rezeptkarte, der der Agent für eine bestimmte Aufgabe folgt. Du startest einen Skill, indem du einen Schrägstrich und seinen Namen tippst, zum Beispiel /grill-with-docs.

🧰

Was du brauchst

  • Einen Coding-Agenten, egal welchen
  • Einen Projektordner, der git nutzt (der Agent committet seine Arbeit)
  • Das war's. Kein GitHub-Konto, kein besonderer Editor.

Ein Wort, das du nicht kennst? Siehe Begriffe am Ende, oder frag deinen Agenten.

⚙️ Einrichtung: einmal pro Projekt, etwa 5 Minuten

Damit wird ein normales Projekt zu einem, in dem dein Agent gut arbeiten kann. Funktioniert bei einem brandneuen oder bestehenden Projekt.

1

Skills installieren (einmal pro Rechner)

Bitte einfach deinen Coding-Agenten:

Installiere die Skills von Matt Pocock von github.com/mattpocock/skills

Die Skills erscheinen nicht im Slash-Menü? Starte deinen Agenten neu.

2

Gib deinem Agenten einen Projektleitfaden: /init

Die meisten Coding-Agenten haben einen init-Befehl. Der Agent durchsucht dein Projekt und schreibt eine Leitfaden-Datei (CLAUDE.md oder AGENTS.md, je nach Agent): wie man es startet, testet und baut, und wo was liegt. Der Agent liest sie zu Beginn jeder Sitzung.

Du kennst diesen Code selbst noch nicht? Der Prompt Führ mich durch dieses Repo gibt dir zuerst eine Übersicht.

3

Skills anbinden: /setup-matt-pocock-skills

Stellt 2–3 Fragen, fügt dann einen Abschnitt „Agent skills" zu deinem Leitfaden hinzu und schreibt ein paar kleine Konfigurationsdateien in docs/agents/.

Wenn gefragt wird, wohin die Tickets kommen, wähle lokale Dateien.

Nicht gefunden? Tippe den vollen Namen: /mattpocock-skills:setup-matt-pocock-skills. Gilt für jeden Skill.

✅ Fertig. Dein Projekt ist bereit für die 5 Schritte unten.

💡 Warum überhaupt einem Workflow folgen?

Der häufigste Grund, warum Programmieren mit KI schiefgeht: Der Agent baut etwas, aber nicht das, was du gemeint hast. Die Lösung: am Anfang langsamer machen. Erst über die Idee einig werden, sie aufschreiben, in kleine Teile schneiden, und erst dann Code schreiben.

Denk an einen Hausbau: 🗣️ Gespräch mit dem Architekten → 📐 Bauplan → 📋 Arbeitsaufträge → 🧱 Bau, mit Kontrollen unterwegs → 🔍 Endabnahme.

🩹 Kleine Änderung? Spring weiter.

Ein Tippfehler, ein Einzeiler, eine Farbkorrektur: Dafür brauchst du keine fünf Schritte. Bitte einfach den Agenten, oder tippe /tdd für einen schnellen Fix mit Test zuerst.

Nimm den ganzen Workflow, wenn es Entscheidungen zu treffen gibt, die Änderung mehrere Dateien betrifft oder länger als eine Sitzung dauert.

📌 Unser Beispiel von Anfang bis Ende: Jemand klaut ständig Mittagessen aus dem Büro-Kühlschrank. Wir bauen eine kleine Kühlschrank-App, mit der du dein Essen beschriftest, einen Diebstahl meldest und die Hauptverdächtigen benennst.

Schritt 1

Grill me (with docs)

/grill-with-docs

Der Agent befragt dich mit vielen Fragen, bis ihr euch einig seid, was genau gebaut wird, und schreibt dabei die Begriffe und großen Entscheidungen des Projekts auf.

🏠 Wie ein guter Architekt, der fragt „Wie viele Schlafzimmer? Große oder kleine Küche?", bevor er irgendetwas zeichnet.

Du
  • Beschreibe deine Idee in einem Satz
  • Beantworte jede Frage (kurze Antworten reichen)
  • Sag „weiß ich nicht", wenn du es nicht weißt. Der Agent schlägt eine Antwort vor.
Agent
  • Fragt in kleinen Runden
  • Gibt zu jeder Frage eine empfohlene Antwort
  • Macht weiter, bis nichts mehr unklar ist
  • Aktualisiert das Glossar (GLOSSARY.md) und hält große Entscheidungen fest
Beispiel
Coding-Agent: fridge-app
Du
/grill-with-docs Jemand isst ständig mein Mittagessen aus dem Büro-Kühlschrank. Ich möchte eine App, um ihn zu erwischen.
Agent

F1: Sollen Diebstahlmeldungen anonym sein? → Ich empfehle ja. Niemand will einen Kühlschrankkrieg mit dem eigenen Namen darauf.

F2: Was, wenn jemand beschuldigt wird, der Joghurt aber wirklich ihm gehörte? → Ich empfehle einen Knopf „Das war meiner", der die Meldung aufhebt.

Du
Anonym, ja. Und bau den Knopf ein. Dave wird ihn brauchen.
Agent

Nächste Runde. F3: Kann ein Essen ablaufen? Ist es nach zwei Wochen noch ein Mittagessen oder ein Wissenschaftsprojekt?…

Was er nebenbei schreibt
GLOSSARY.mdMittagessen: ein beschriftetes Essen, mit Besitzer und Datum. Meldung: eine anonyme Behauptung, dass jemand ein Mittagessen genommen hat, das ihm nicht gehörte.

Warum das wichtig ist: Beim nächsten Mal benutzt ihr dieselben Wörter für dieselben Dinge. Weniger Missverständnisse, kürzere Antworten. (Das einfache /grill-me macht die Befragung ohne die Dokumente. Praktisch für Themen ohne Code.)

💡

Tipp: Diesen Schritt lassen viele aus, und er ist der wichtigste. Zehn Minuten Fragen sparen Stunden, in denen das Falsche repariert wird. Bei einer Frage verloren? Öffne ein neues Fenster und füge den Prompt Einfach erklären ein.

Schritt 2

Die Spec schreiben

/to-spec

Der Agent macht aus eurem Gespräch einen schriftlichen Plan (eine „Spec"). Keine neuen Fragen: Er schreibt nur auf, was ihr vereinbart habt.

🏠 Der Bauplan. Alle können später nachsehen und prüfen: „Ist das, was wir besprochen haben?"

Du
  • Starte ihn direkt nach der Befragung, im selben Chat
  • Bestätige, wie der Agent die Funktion testen will
  • Lies die Spec. Korrigiere, was falsch ist.
Agent
  • Sieht sich deinen Code an
  • Listet auf, was nicht dazugehört
Beispiel: was der Agent schreibt
.scratch/fridge-thief/spec.md## Problem Mittagessen verschwinden aus dem Büro-Kühlschrank. Niemand weiß, wer es ist. ## Lösung Beschrifte dein Essen. Melde einen Diebstahl, anonym. Ein „Most wanted"-Board zeigt die Hauptverdächtigen. ## User Stories 1. Als Kollege möchte ich mein Essen mit meinem Namen und dem Datum beschriften… 2. Als Opfer möchte ich ein gestohlenes Essen melden, ohne meinen Namen zu nennen… 3. Als beschuldigter Kollege möchte ich sagen können „das war meiner"… 4. Als jeder möchte ich das „Most wanted"-Board sehen… ## Nicht im Umfang Kühlschrank-Kameras, Fingerabdrücke auf dem Joghurt.
💡

Tipp: Die Spec ist dein Dokument. Wenn etwas nicht stimmt, sag es jetzt. Einen Satz zu korrigieren ist viel billiger, als Code zu korrigieren.

🎟️
Schritt 3

In Tickets schneiden

/to-tickets

Der Agent teilt die Spec in kleine Tickets auf. Jedes ist ein kleines Stück, das für sich allein funktioniert.

🏠 Arbeitsaufträge: „Sanitär für die Küche", „Elektrik fürs Schlafzimmer". Ein Team, eine Aufgabe, ein Tag.

✅ Gut: Stücke

01
02
03

Jedes Ticket geht durch alle Schichten (Oberfläche, Logik, Speichern) für eine kleine Funktion. Du kannst es ausprobieren, sobald es fertig ist.

❌ Schlecht: Schichten

alle Oberflächen
die ganze Logik
das ganze Speichern

„Erst alle Oberflächen, dann die ganze Logik…" Bis ganz zum Schluss funktioniert nichts.

Du
  • Prüfe die vorgeschlagene Liste
  • Zu groß? Zu klein? Lass teilen oder zusammenlegen.
  • Gib frei
Agent
  • Schlägt die Tickets vor, in Reihenfolge
  • Sagt, welches Ticket auf welches warten muss
  • Speichert eine Datei pro Ticket
Beispiel: die Tickets für die Kühlschrank-App
01
Dein Essen beschriften
Wartet auf: nichts, sofort starten
02
Ein gestohlenes Essen melden, mit einem Knopf „Das war meiner"
Wartet auf: 01
03
„Most wanted"-Board
Wartet auf: 02

Gespeichert als .scratch/fridge-thief/issues/01-label-lunch.md, 02-…, 03-…

💡

Tipp: Jedes Ticket ist so bemessen, dass es in eine frische Agent-Sitzung passt. Kleine Tickets heißen: Der Agent bleibt fokussiert und macht weniger Fehler.

🛠️
Schritt 4

Bauen, Test zuerst (TDD)

/implement

Der Agent baut ein Ticket und schreibt dabei zuerst den Test, dann den Code, der ihn bestehen lässt.

🏠 Bevor eine Wand gebaut wird, schreibt man die Prüfung auf: „Die Wand muss gerade sein." Bauen. Prüfen. Nächste Wand.

Die TDD-Schleife (testgetriebene Entwicklung)

🔴 RotSchreibe einen Test für ein kleines Verhalten.
Er schlägt fehl, weil der Code noch nicht existiert.
→
🟢 GrünSchreibe gerade genug Code,
damit der Test besteht.
↻
WiederholenNächstes kleines Verhalten,
bis das Ticket fertig ist.

Warum? Tests geben dem Agenten einen Beweis, dass sein Code funktioniert, statt es nur zu glauben. Ohne Tests tappt er im Dunkeln.

Du
  • Starte eine frische Sitzung (/clear, /new oder ein neuer Chat). Deine Dateien bleiben; das Ticket sagt dem Agenten, was er braucht.
  • Gib dem Agenten ein Ticket
  • Vereinbart, was getestet wird
  • Schau zu, und greif ein, wenn er vom Weg abkommt
Agent
  • Durchläuft die Schleife Rot → Grün
  • Lässt am Ende alle Tests laufen
  • Startet das Review (Schritt 5) selbst
  • Sichert dann die Arbeit (Git-Commit)
Beispiel
Coding-Agent: fridge-app (frische Sitzung)
Du
/clear
/implement .scratch/fridge-thief/issues/01-label-lunch.md
Agent

🔴 Test: „Ein beschriftetes Essen zeigt den Namen seines Besitzers". Schlägt fehl, wie erwartet.

🟢 Beschriftungsformular und Essensliste hinzugefügt. Test besteht.

🔴 Test: „Ein Essen ohne Namen kann nicht gespeichert werden"… 🟢 besteht.

✅ Alle Tests bestehen. Starte das Review… dann committe ich.

⚡ Schnellere Option: alle Tickets auf einmal mit /implement-spec

Statt einem Ticket pro Sitzung startet der Agent mehrere Helfer-Agenten parallel. Jeder arbeitet in seiner eigenen Kopie des Projekts, ein Ticket pro Helfer, Test zuerst. Ist ein Ticket fertig, wird seine Arbeit zurückgemergt. Wartende Tickets starten, sobald ihre Blocker fertig sind. Am Ende gibt es ein Review für alles.

Am besten bei vielen Tickets. Fang mit /implement an, ein Ticket nach dem anderen, bis sich der Ablauf natürlich anfühlt. So ist es leichter zu verfolgen und zu steuern.

💡

Tipp: Die Sitzung wird lang, oder der Agent vergisst Dinge? Tippe /handoff: Der Agent schreibt eine kurze Notiz für die nächste Sitzung. Dann /clear und frisch weitermachen.

🔍
Schritt 5

Code-Review

/code-review

Der Agent prüft die Arbeit: Ist der Code sauber, und tut er, was das Ticket verlangt, nicht mehr?

🏠 Die Endabnahme: nach Vorschrift gebaut und passt zum Bauplan.

Du
  • Probiere die Funktion selbst aus
  • Lies den Bericht
  • Entscheide, was behoben wird: „behebe 1, ignoriere 2"
Agent
  • Meldet Befunde, ohne selbst etwas zu ändern
  • Behebt, was du auswählst
Beispiel: Review-Bericht
## Review (2 Befunde) 1. Unklarer Name: Variable `l` sollte `lunch` heißen. 2. Zu viel: einen Upload für „Kühlschrank-Kamera" hinzugefügt. Laut Spec ist das nicht im Umfang.
🔁

Nächstes Ticket? Zurück zu Schritt 4.

Frische Sitzung → /implement Ticket 02 → Review → Ticket 03… bis alle Tickets fertig sind. 🎉

Begriffe

Kontext
Woran sich der Agent in der aktuellen Sitzung erinnert. Ist er voll, wird der Agent schlechter.
Frische Sitzung
Ein neuer Chat mit leerem Kontext. Deine Dateien ändern sich nicht.
Projektleitfaden
Eine Datei (AGENTS.md oder CLAUDE.md), die der Agent zu Beginn jeder Sitzung liest.
Spec
Der schriftliche Plan: was gebaut wird, und was nicht.
Nicht im Umfang
Was ihr vereinbart habt, diesmal nicht zu bauen.
Ticket
Ein kleines Stück der Spec, das für sich allein funktioniert.
Test
Ein bisschen Code, der prüft, ob anderer Code tut, was er soll.
TDD
Testgetriebene Entwicklung: erst den Test schreiben, ihn fehlschlagen sehen, dann den Code schreiben.
Commit
Ein gesicherter Schnappschuss des Projekts in git. Du kannst jederzeit dorthin zurück.

Noch etwas unklar? Frag deinen Agenten: „Erkläre [Wort] einfach." Oder nutze den Prompt Einfach erklären.
