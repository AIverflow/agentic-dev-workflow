Before you start

The basics

🤖

What is a coding agent?

An AI assistant that works inside your project folder. It can read your files, write code, and run commands, like a teammate sitting at your computer. Examples: Claude Code, Codex, Cursor, Hermes Agent.

🧩

What is a skill?

A recipe card the agent follows for one job. You start a skill by typing a slash and its name, like /grill-with-docs.

🧰

What you need

  • A coding agent, any of them
  • A project folder that uses git (the agent commits its work)
  • That's it. No GitHub account, no special editor.

A word you don't know? See Words at the end, or ask your agent.

⚙️ Setup: once per project, about 5 minutes

This turns a normal project into one your agent can work in well. Works on a brand-new or an existing project.

1

Install the skills (once per computer)

Just ask your coding agent:

Install Matt Pocock's skills from github.com/mattpocock/skills

Skills don't show up in the slash menu? Restart your agent.

2

Give your agent a project guide: /init

Most coding agents have an init command. The agent scans your project and writes a guide file (CLAUDE.md or AGENTS.md, depending on the agent): how to run, test and build it, and where things live. The agent reads it at the start of every session.

New to this code yourself? The Walk me through this repo prompt gives you a map first.

3

Connect the skills: /setup-matt-pocock-skills

Asks 2–3 questions, then adds an "Agent skills" section to your guide and writes small config files in docs/agents/.

When it asks where tickets go, pick local files.

Not found? Type the full name: /mattpocock-skills:setup-matt-pocock-skills. Same for every skill.

✅ Done. Your project is ready for the 5 steps below.

💡 Why follow a workflow at all?

The #1 way AI coding goes wrong: the agent builds something, but not what you meant. The fix is to slow down at the start. Agree on the idea first, write it down, cut it into small pieces, and only then write code.

Think of building a house: 🗣️ talk with the architect → 📐 blueprint → 📋 work orders → 🧱 build, with checks along the way → 🔍 final inspection.

🩹 Small change? Skip ahead.

A typo, a one-line fix, a color tweak: you don't need five steps. Just ask the agent, or type /tdd for a quick test-first fix.

Use the full workflow when there are choices to make, the change touches several files, or it takes more than one session.

📌 Our example all the way down: someone keeps stealing lunches from the office fridge. We build a small fridge app to label your lunch, report a theft, and name the top suspects.

🔥
Step 1

Grill me (with docs)

/grill-with-docs

The agent interviews you with lots of questions until you both agree on exactly what to build, and writes down the project's words and big decisions as you go.

🏠 Like a good architect asking "How many bedrooms? Big kitchen or small?" before drawing anything.

You
  • Describe your idea in one sentence
  • Answer each question (short answers are fine)
  • Say "I don't know" when you don't. The agent suggests an answer.
Agent
  • Asks questions in small rounds
  • Gives a recommended answer for each one
  • Keeps going until nothing is left unclear
  • Updates the glossary (GLOSSARY.md) and notes big decisions
Example
Coding agent: fridge-app
You
/grill-with-docs Someone keeps eating my lunch from the office fridge. I want an app to catch them.
Agent

Q1: Should theft reports be anonymous? → I recommend yes. Nobody wants a fridge war with their name on it.

Q2: What if someone is accused but the yogurt was really theirs? → I recommend a "That was mine" button that cancels the report.

You
Anonymous, yes. And add the button. Dave will need it.
Agent

Next round. Q3: Can a lunch expire? After two weeks, is it still a lunch, or a science project?…

What it writes as it goes
GLOSSARY.mdLunch: a labeled food item, with an owner and a date. Report: an anonymous claim that someone took a lunch that wasn't theirs.

Why it matters: next time, you and the agent use the same words for the same things. Fewer misunderstandings, shorter answers. (Plain /grill-me does the interview without the docs. Handy for non-code topics.)

💡

Tip: this is the step people skip, and the one that matters most. Ten minutes of questions saves hours of fixing the wrong thing. Lost on a question? Open a new window and paste the Explain it simply prompt.

📄
Step 2

Write the spec

/to-spec

The agent turns your conversation into a written plan (a "spec"). No new questions, it just writes down what you agreed.

🏠 The blueprint. Everyone can look at it later and check "is this what we said?"

You
  • Run it right after grilling, in the same chat
  • Confirm how the agent plans to test the feature
  • Read the spec. Fix anything wrong.
Agent
  • Looks through your code
  • Lists what is out of scope
Example: what the agent writes
.scratch/fridge-thief/spec.md## Problem Lunches keep disappearing from the office fridge. Nobody knows who. ## Solution Label your lunch. Report a theft, anonymously. A "Most wanted" board shows the top suspects. ## User stories 1. As a coworker, I want to label my lunch with my name and the date… 2. As a victim, I want to report a stolen lunch without giving my name… 3. As an accused coworker, I want to say "that was mine"… 4. As anyone, I want to see the "Most wanted" board… ## Out of scope Fridge cameras, fingerprinting the yogurt.
💡

Tip: the spec is your document. If something is wrong, say so now. Fixing a sentence is much cheaper than fixing code.

🎟️
Step 3

Cut it into tickets

/to-tickets

The agent splits the spec into small tickets. Each one is a little piece that works on its own.

🏠 Work orders: "plumbing for the kitchen", "wiring for the bedroom". One crew, one job, one day.

✅ Good: slices

01
02
03

Each ticket goes through every layer (screen, logic, saving) for one small feature. You can try it as soon as it's done.

❌ Bad: layers

all screens
all logic
all saving

"Do all the screens, then all the logic…" Nothing works until the very end.

You
  • Check the proposed list
  • Too big? Too small? Ask to split or merge.
  • Approve
Agent
  • Proposes the tickets, in order
  • Says which ticket must wait for which
  • Saves one file per ticket
Example: the tickets for the fridge app
01
Label your lunch
Waits for: nothing, start now
02
Report a stolen lunch, with a "That was mine" button
Waits for: 01
03
"Most wanted" board
Waits for: 02

Saved as .scratch/fridge-thief/issues/01-label-lunch.md, 02-…, 03-…

💡

Tip: each ticket is sized to fit in one fresh agent session. Small tickets mean the agent stays focused and makes fewer mistakes.

🛠️
Step 4

Build it, test-first (TDD)

/implement

The agent builds one ticket, writing the test first, then the code that makes it pass.

🏠 Before building a wall, write down the check: "the wall must be straight". Build. Check. Next wall.

The TDD loop (Test-Driven Development)

🔴 RedWrite a test for one small behavior.
It fails, because the code doesn't exist yet.
→
🟢 GreenWrite just enough code
to make the test pass.
↻
RepeatNext small behavior,
until the ticket is done.

Why? Tests give the agent proof that its code works, instead of just believing it. Without tests, it's flying blind.

You
  • Start a fresh session (/clear, /new, or a new chat). Your files stay; the ticket tells the agent what it needs.
  • Point the agent at one ticket
  • Agree on what gets tested
  • Watch, and step in if it goes off track
Agent
  • Runs the red → green loop
  • Runs all the tests at the end
  • Calls the review (step 5) on its own
  • Then saves the work (git commit)
Example
Coding agent: fridge-app (fresh session)
You
/clear
/implement .scratch/fridge-thief/issues/01-label-lunch.md
Agent

🔴 Test: "a labeled lunch shows its owner's name". Fails, as expected.

🟢 Added the label form and the lunch list. Test passes.

🔴 Test: "a lunch with no name can't be saved"… 🟢 passes.

✅ All tests pass. Running the review… then I'll commit.

⚡ Faster option: all tickets at once with /implement-spec

Instead of one ticket per session, the agent runs several helper agents in parallel. Each works in its own copy of the project, one ticket each, test-first. When a ticket is done, its work is merged back. Tickets that were waiting start as soon as their blockers finish. At the end, one review of everything.

Best when you have many tickets. Start with /implement one ticket at a time until the flow feels natural. It's easier to follow and to steer.

💡

Tip: session getting long, or the agent forgetting things? Type /handoff: the agent writes a short note for the next session. Then /clear and continue fresh.

🔍
Step 5

Code review

/code-review

The agent checks the work: is the code clean, and does it do what the ticket asked, nothing more?

🏠 The final inspection: built to code, and matches the blueprint.

You
  • Try the feature yourself
  • Read the report
  • Decide what to fix: "fix 1, ignore 2"
Agent
  • Reports findings, without fixing on its own
  • Fixes what you pick
Example: review report
## Review (2 findings) 1. Unclear name: variable `l` should be `lunch`. 2. Extra: added a "fridge camera" upload. The spec says it's out of scope.
🔁

Next ticket? Back to step 4.

Fresh session → /implement ticket 02 → review → ticket 03… until all tickets are done. 🎉

One line each

Words

Context
What the agent remembers in the current session. When it fills up, the agent gets worse.
Fresh session
A new chat with empty context. Your files don't change.
Project guide
A file (AGENTS.md or CLAUDE.md) the agent reads at the start of every session.
Spec
The written plan: what to build, and what not to build.
Out of scope
What you agreed not to build this time.
Ticket
One small piece of the spec that works on its own.
Test
A bit of code that checks another bit of code does what it should.
TDD
Test-driven development: write the test first, watch it fail, then write the code.
Commit
A saved snapshot of the project in git. You can always go back to it.

Something else unclear? Ask your agent: "Explain [word] simply." Or use the Explain it simply prompt.
