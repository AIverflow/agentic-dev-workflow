基础知识

🤖

什么是编程智能体？

一个在你的项目文件夹里工作的 AI 助手。它能读你的文件、写代码、运行命令，就像一位坐在你电脑前的同事。例如：Claude Code、Codex、Cursor、Hermes Agent。

🧩

什么是 skill？

一张智能体为完成某项任务而遵循的菜谱卡。输入斜杠加上名字就能启动一个 skill，例如 /grill-with-docs。

🧰

你需要什么

  • 一个编程智能体，哪个都行
  • 一个使用 git 的项目文件夹（智能体会提交它的工作）
  • 就这些。不需要 GitHub 账号，也不需要特别的编辑器。

遇到不认识的词？看最后的词汇，或者问你的智能体。

⚙️ 安装配置：每个项目一次，大约 5 分钟

把一个普通项目变成智能体能顺利工作的项目。新项目和已有项目都适用。

1

安装 skills （每台电脑一次）

直接对你的编程智能体说：

Install Matt Pocock's skills from github.com/mattpocock/skills

斜杠菜单里没有出现这些 skill？重启你的智能体。

2

给智能体一份项目指南：/init

大多数编程智能体都有 init 命令。智能体会扫描你的项目，写一份指南文件（CLAUDE.md 或 AGENTS.md，取决于智能体）：如何运行、测试、构建，以及各部分在哪里。智能体每次会话开始时都会读它。

自己也不熟悉这份代码？先用带我了解这个仓库提示词，它会先给你一张地图。

3

接入 skills：/setup-matt-pocock-skills

它会问 2–3 个问题，然后在你的指南里加一个 "Agent skills" 小节，并在 docs/agents/ 中写入几个小配置文件。

当它问工单放在哪里时，选本地文件。

找不到？输入完整名称：/mattpocock-skills:setup-matt-pocock-skills。每个 skill 都一样。

✅ 完成。你的项目已经可以开始下面的 5 个步骤了。

💡 为什么要遵循一个工作流？

AI 编程出问题的头号原因：智能体做出了东西，但不是你想要的。解决办法是一开始放慢速度：先就想法达成一致，写下来，切成小块，然后才写代码。

想想盖房子：🗣️ 和建筑师沟通 → 📐 蓝图 → 📋 施工单 → 🧱 施工，过程中不断检查 → 🔍 竣工验收。

🩹 改动很小？直接跳过。

一个错别字、一行修复、调一下颜色：不需要走五步。直接让智能体做，或者输入 /tdd 来一次快速的测试先行修复。

当有需要做的选择、改动涉及多个文件，或者一次会话做不完时，才用完整的工作流。

📌 贯穿全文的例子：有人老是偷吃午饭，偷的是办公室冰箱里的。我们来做一个小小的冰箱应用：给午饭贴标签、举报偷吃、点名头号嫌疑人。

🔥
第 1 步

Grill me (with docs)

/grill-with-docs

智能体会不断向你提问，直到你们对要做的东西完全达成一致，同时把项目的术语和重大决策记录下来。

🏠 就像一位好建筑师，在动笔画图之前先问："要几间卧室？厨房大还是小？"

你
  • 用一句话描述你的想法
  • 回答每个问题（简短回答就行）
  • 不知道就说"不知道"，智能体会给出建议答案。
智能体
  • 分小轮提问
  • 每个问题都给出推荐答案
  • 一直问到没有不清楚的地方
  • 更新术语表（GLOSSARY.md）并记下重大决策
示例
编程智能体：fridge-app
你
/grill-with-docs 有人老是偷吃我放在办公室冰箱里的午饭。我想做个应用把他揪出来。
智能体

问 1：举报要匿名吗？→ 我建议匿名。没人想带着自己的名字卷进冰箱大战。

问 2：如果有人被冤枉了，酸奶其实是他自己的呢？→ 我建议加一个"那是我的"按钮，点了就撤销举报。

你
要匿名。按钮也加上。Dave 肯定用得上。
智能体

下一轮。问 3：午饭会过期吗？放了两周之后，它还算午饭，还是算科学实验？……

它顺手写下的内容
GLOSSARY.md午饭：一份贴了标签的食物，有主人，有日期。 举报：一条匿名的指控，称有人拿走了不属于自己的午饭。

为什么重要：下次你和智能体会用同样的词指同样的东西。误解更少，回答更短。（普通的 /grill-me 只做访谈，不写文档，适合与代码无关的话题。）

💡

提示：这是大家最常跳过、却最重要的一步。十分钟的提问，能省下好几个小时修错东西的时间。被某个问题难住了？开一个新窗口，粘贴简单讲解提示词。

📄
第 2 步

写 spec（需求规格）

/to-spec

智能体把你们的对话变成一份书面计划（即 "spec"）。不再提新问题，只是把你们达成的共识写下来。

🏠 这就是蓝图。以后任何人都能翻出来核对："这是我们当时说的吗？"

你
  • 在访谈结束后、同一个对话里立刻运行
  • 确认智能体打算怎么测试这个功能
  • 读一遍 spec，改掉不对的地方
智能体
  • 浏览你的代码
  • 列出不在范围内的内容
示例：智能体写出的内容
.scratch/fridge-thief/spec.md## 问题 办公室冰箱里的午饭老是不翼而飞。没人知道是谁干的。 ## 方案 给午饭贴标签。匿名举报偷吃。一块"头号通缉"榜单显示头号嫌疑人。 ## 用户故事 1. 作为同事，我想在午饭上贴上我的名字和日期…… 2. 作为受害者，我想不留名地举报午饭被偷…… 3. 作为被指控的同事，我想说"那是我的"…… 4. 作为任何人，我想看到"头号通缉"榜单…… ## 不在范围内 冰箱摄像头、给酸奶采指纹。
💡

提示：spec 是你的文档。哪里不对，现在就说。改一句话比改代码便宜得多。

🎟️
第 3 步

切分成工单

/to-tickets

智能体把 spec 拆成小工单（ticket）。每一个都是能独立运行的小块。

🏠 施工单："厨房水管"、"卧室电路"。一个班组，一项任务，一天完成。

✅ 好：竖切

01
02
03

每个工单为一个小功能贯穿所有层（界面、逻辑、存储）。一完成就能试用。

❌ 差：横切

所有界面
所有逻辑
所有存储

"先做完所有界面，再做所有逻辑……" 直到最后一刻都没有能跑的东西。

你
  • 检查建议的列表
  • 太大？太小？让它拆分或合并。
  • 批准
智能体
  • 按顺序提出工单
  • 标明哪个工单要等哪个
  • 每个工单存成一个文件
示例：冰箱应用的工单
01
给你的午饭贴标签
等待：无，马上开始
02
举报午饭被偷，附带"那是我的"按钮
等待：01
03
"头号通缉"榜单
等待：02

保存为 .scratch/fridge-thief/issues/01-label-lunch.md、02-…、03-…

💡

提示：每个工单的大小都能放进一次全新的智能体会话。工单小，智能体就更专注，出错更少。

🛠️
第 4 步

动手实现，测试先行（TDD）

/implement

智能体一次实现一个工单：先写测试，再写让测试通过的代码。

🏠 砌墙之前，先写下检查标准："墙必须是直的"。砌墙。检查。下一面墙。

TDD 循环（测试驱动开发）

🔴 红为一个小行为写测试。
它会失败，因为代码还不存在。
→
🟢 绿只写刚好够用的代码，
让测试通过。
↻
重复下一个小行为，
直到工单完成。

为什么？测试给了智能体代码能用的证据，而不是凭感觉相信。没有测试，它就是在盲飞。

你
  • 开启一个全新会话（/clear、/new 或新对话）。你的文件还在；工单会告诉智能体它需要知道的一切。
  • 给智能体指定一个工单
  • 商定要测试什么
  • 看着它做，偏离方向时及时介入
智能体
  • 执行红 → 绿循环
  • 最后运行全部测试
  • 自己启动评审（第 5 步）
  • 然后保存工作（git commit）
示例
编程智能体：fridge-app（全新会话）
你
/clear
/implement .scratch/fridge-thief/issues/01-label-lunch.md
智能体

🔴 测试："贴了标签的午饭会显示主人的名字"。如预期失败。

🟢 加上了标签表单和午饭列表。测试通过。

🔴 测试："没有名字的午饭不能保存"… 🟢 通过。

✅ 全部测试通过。正在运行评审…然后我会提交。

⚡ 更快的选项：用 /implement-spec 一次完成所有工单

不再是一个会话一个工单，而是由智能体同时启动多个助手智能体。每个助手在自己的项目副本里工作，各负责一个工单，同样测试先行。一个工单完成后，它的工作会合并回来。等待中的工单在其依赖完成后立即开始。最后对全部内容做一次评审。

工单很多时最合适。建议先用 /implement 一次做一个工单，等熟悉流程后再用。这样更容易跟上，也更容易掌控。

💡

提示：会话越来越长，或者智能体开始忘事？输入 /handoff：智能体会为下一次会话写一份简短的交接说明。然后 /clear，从头继续。

🔍
第 5 步

代码评审

/code-review

智能体检查这份工作：代码干净吗，以及它做到了工单的要求吗，而且没有多做？

🏠 竣工验收：符合建筑规范，也和蓝图一致。

你
  • 亲自试用这个功能
  • 阅读报告
  • 决定修什么："修 1，忽略 2"
智能体
  • 报告发现的问题，不擅自修改
  • 修复你选中的问题
示例：评审报告
## 评审 （2 项发现） 1. 命名不清楚：变量 `l` 应该叫 `lunch`。 2. 多余：加了一个"冰箱摄像头"上传功能。spec 里写明它不在范围内。
🔁

下一个工单？回到第 4 步。

全新会话 → /implement 工单 02 → 评审 → 工单 03… 直到所有工单完成。🎉

黄金法则：先沟通，后编码。小步前进，每个工单一个全新会话，用测试作证据。

每个词一句话

词汇

上下文
智能体在当前会话中记得的内容。装满之后，智能体会变差。
全新会话
一个上下文为空的新对话。你的文件不会变。
项目指南
智能体每次会话开始时都会读的一个文件（AGENTS.md 或 CLAUDE.md）。
Spec
书面计划：要做什么，以及不做什么。
不在范围内
你们约定这次不做的内容。
工单
spec 中一个能独立运行的小块。
测试
一小段代码，用来检查另一段代码是否做了它该做的事。
TDD
测试驱动开发：先写测试，看它失败，再写代码。
提交（commit）
git 中保存的一份项目快照。你随时可以回到它。

还有别的看不懂？问你的智能体："请简单解释[词语]。"或者使用简单讲解提示词。

基于 Matt Pocock 的 skills，适用于编程智能体。 内容对应 1.3.1 版本（2026 年 10 月）。
