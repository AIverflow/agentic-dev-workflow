Before you start

The basics

🤖

What is a coding agent?

An AI assistant that works inside your project folder. It can read your files, write code, and run commands, like a teammate sitting at your computer. Examples: Claude Code, Codex, Cursor.

🧩

What is a skill?

A recipe card the agent follows for one job. You start a skill by typing a slash and its name, like /grill-with-docs.

⚙️ Setup: once per project, about 5 minutes

This turns a normal project into one your agent can work in well. Works on a brand-new or an existing project.

1

Install the skills (once per computer)

Just ask your coding agent:

Install Matt Pocock's skills (mattpocock-skills, from the official Claude plugins marketplace).

Works with most coding agents. Source: github.com/mattpocock/skills

2

Give your agent a project guide: /init

Most coding agents have an init command. The agent scans your project and writes a guide file (CLAUDE.md or AGENTS.md, depending on the agent): how to run, test and build it, and where things live. The agent reads it at the start of every session.

3

Connect the skills: /setup-matt-pocock-skills

Asks 2–3 questions, then adds an "Agent skills" section to your guide and writes small config files in docs/agents/.

When it asks where tickets go, pick local files. No GitHub account needed.

✅ Done. Your project is ready for the 6 steps below.

💡 Why follow a workflow at all?

The #1 way AI coding goes wrong: The agent builds something, but not what you meant. The fix is to slow down at the start. Agree on the idea first, write it down, cut it into small pieces, and only then write code.

Think of building a house: 🗣️ talk with the architect → 📐 blueprint → 📋 work orders → 🧱 build, with checks along the way → 🔍 final inspection → 🪞 team debrief.

🔥 Grill with docs→ 📄 Spec→ 🎟️ Tickets→ 🛠️ Build + TDD→ 🔍 Review→ 🪞 Retro

📌 Our example all the way down: adding dark mode to a simple todo-list app.

🔥
Step 1

Grill me (with docs)

/grill-with-docs

The agent interviews you with lots of questions until you both agree on exactly what to build, and writes down the project's words and big decisions as you go.

🏠 Like a good architect asking "How many bedrooms? Big kitchen or small?" before drawing anything.

You
  • Describe your idea in one sentence
  • Answer each question (short answers are fine)
  • Say "I don't know" when you don't. The agent suggests an answer.
Agent
  • Asks questions in small rounds
  • Gives a recommended answer for each one
  • Keeps going until nothing is left unclear
  • Updates the glossary (GLOSSARY.md) and decision notes (docs/adr/)
Example
Coding agent: todo-app
You
/grill-with-docs I want to add dark mode to my todo app
Agent

Q1: Should it follow the computer's own light/dark setting, or use a toggle button? → I recommend both: follow the computer by default, with a button to override.

Q2: Should the app remember your choice after a reload? → Yes.

You
Both, yes. And yes, remember it.
Agent

Next round. Q3: Where should the button go?…

What it writes as it goes
GLOSSARY.mdTheme: the color set the app uses, "light" or "dark". System theme: the light/dark setting of the user's computer.

Why it matters: next time, you and the agent use the same words for the same things. Fewer misunderstandings, shorter answers. (Plain /grill-me does the interview without the docs. Handy for non-code topics.)

💡

Tip: this is the step people skip, and the one that matters most. Ten minutes of questions saves hours of fixing the wrong thing. Use it every time.

📄
Step 2

Write the spec

/to-spec

The agent turns your conversation into a written plan (a "spec"). No new questions, it just writes down what you agreed.

🏠 The blueprint. Everyone can look at it later and check "is this what we said?"

You
  • Run it right after grilling, in the same chat
  • Confirm how the agent plans to test the feature
  • Read the spec. Fix anything wrong.
Agent
  • Looks through your code
  • Writes the spec to a file
  • Lists what is out of scope too
Example: what the agent writes
.scratch/dark-mode/spec.md## Problem The app is too bright at night. ## Solution A dark theme that follows the computer setting, with a toggle button. ## User stories 1. As a user, I want the app dark when my computer is in dark mode… 2. As a user, I want a button to switch theme… 3. As a user, I want my choice remembered after reload… ## Out of scope Custom colors, scheduled dark mode at sunset.
💡

Tip: the spec is your document. If something is wrong, say so now. Fixing a sentence is much cheaper than fixing code.

🎟️
Step 3

Cut it into tickets

/to-tickets

The agent splits the spec into small tickets. Each one is a little piece that works on its own.

🏠 Work orders: "plumbing for the kitchen", "wiring for the bedroom". One crew, one job, one day.

✅ Good: slices

01
02
03

Each ticket goes through every layer (screen, logic, saving) for one small feature. You can try it as soon as it's done.

❌ Bad: layers

all screens
all logic
all saving

"Do all the screens, then all the logic…" Nothing works until the very end.

You
  • Check the proposed list
  • Too big? Too small? Ask to split or merge.
  • Approve
Agent
  • Proposes the tickets, in order
  • Says which ticket must wait for which
  • Saves one file per ticket
Example: the tickets for dark mode
01
Toggle button switches the theme
Waits for: nothing, start now
02
Remember the choice after reload
Waits for: 01
03
Follow the computer setting by default
Waits for: 01

Saved as .scratch/dark-mode/issues/01-toggle-button.md, 02-…, 03-…

💡

Tip: each ticket is sized to fit in one fresh agent session. Small tickets mean the agent stays focused and makes fewer mistakes.

🛠️
Step 4

Build it, test-first (TDD)

/implement

The agent builds one ticket, writing the test first, then the code that makes it pass.

🏠 Before building a wall, write down the check: "the wall must be straight". Build. Check. Next wall.

The TDD loop (Test-Driven Development)

🔴 RedWrite a test for one small behavior.
It fails, because the code doesn't exist yet.
→
🟢 GreenWrite just enough code
to make the test pass.
↻
RepeatNext small behavior,
until the ticket is done.

Why? Tests give the agent proof that its code works, instead of just believing it. Without tests, it's flying blind.

You
  • Start a fresh session (/clear or a new chat)
  • Point the agent at one ticket
  • Agree on what gets tested
  • Watch, and step in if it goes off track
Agent
  • Runs the red → green loop
  • Runs all the tests at the end
  • Calls the review (step 5) on its own
  • Saves the work (git commit)
Example
Coding agent: todo-app (fresh session)
You
/clear
/implement .scratch/dark-mode/issues/01-toggle-button.md
Agent

🔴 Test: "clicking the theme button makes the page dark". Fails, as expected.

🟢 Added the button and dark colors. Test passes.

🔴 Test: "clicking twice goes back to light"… 🟢 passes.

✅ All tests pass. Committed. Running the review…

⚡ Faster option: all tickets at once with /implement-spec

Instead of one ticket per session, the agent runs several helper agents in parallel. Each works in its own copy of the project, one ticket each, test-first. When a ticket is done, its work is merged into one shared branch. Tickets that were waiting start as soon as their blockers finish. At the end, one review of everything.

Best when you have many tickets. Start with /implement one ticket at a time until the flow feels natural. It's easier to follow and to steer.

💡

Tip: want test-first on a quick fix outside this flow? Just type /tdd. It's the same loop.

🔍
Step 5

Code review

/code-review

Two separate reviewers check the work. Is the code clean? And does it do what the ticket asked?

🏠 The final inspection. One inspector checks building codes, another checks it matches the blueprint.

📏 Standards

Does the code follow the project's rules? Clear names? No copy-pasted code? Nothing overcomplicated?

🎯 Spec

Does it do everything the ticket asked, and nothing more? Anything missing, wrong, or extra?

You
  • Read both reports
  • Decide what to fix: "fix 1 and 3, ignore 2"
Agent
  • Runs both reviewers side by side
  • Reports findings, without fixing on its own
  • Fixes what you pick
Example: review report
## Standards (1 finding) - Possible unclear name: variable `t` should be `theme`. ## Spec (1 finding) - Extra: added a "sepia" theme, which the ticket didn't ask for.
💡

Tip: /implement runs the review for you at the end. To run it yourself, give a starting point, like /code-review main (everything since the main branch).

🔁

Next ticket? Back to step 4.

Fresh session → /implement ticket 02 → review → ticket 03… until all tickets are done. Then step 6. 🎉

⚡ Lots of tickets? /implement-spec runs this whole loop at once, in parallel, with one review at the end (see step 4).

🪞
Step 6

Retro: learn from the session

/retro

The agent looks back at how the work went and suggests ways to improve its own setup, so the next feature goes smoother. It changes the setup, not the code.

🏠 The team debrief after the house is done: "What slowed us down? What should we check automatically next time?"

You
  • Run it when all tickets are done, or after a bumpy session
  • Pick which suggestions to apply
Agent
  • Re-reads the session
  • Finds what went slow or wrong
  • Suggests fixes, most important first

What it looks for

🧭

Finding things

Did the agent waste time looking for files? Add a pointer in the project guide.

🚦

Automatic checks

Could a linter, a test or a pre-commit check have caught a mistake? Add it.

📏

Rules

Did the review miss something? Add a rule to the coding standards, or remove a useless one.

Example
Coding agent: todo-app
You
/retro
Agent

1. Automatic checks: I committed once with a failing test. Add a pre-commit check that runs the tests.

2. Finding things: I searched 6 files for the color settings. Add one line to AGENTS.md: "Theme colors live in styles/theme.css".

You
Do both.
💡

Tip: each retro makes the agent a bit better at your project. Small fixes add up fast.
